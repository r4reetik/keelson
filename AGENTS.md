# AGENTS.md

Read this first. It holds the decisions behind this project and the rules for changing it. It is written for coding agents (Claude Code reads it through `CLAUDE.md`; Codex, Cursor, Copilot and others read `AGENTS.md` directly) and for people.

It sits on top of the human docs and doesn't repeat them: [CONTRIBUTING.md](CONTRIBUTING.md) covers setup and adding a check; [docs/architecture.md](docs/architecture.md) covers how a scan works; [docs/releasing.md](docs/releasing.md) covers releases; [docs/deployment.md](docs/deployment.md) covers running it; [docs/networks.md](docs/networks.md) covers scanning through a VPN or zero trust network.

## Keep this file current

This file is part of the code. It is only useful while it is true, so every change keeps it true:

1. **In the same commit** as any change that makes, changes or reverses a decision, update the section it affects and add a dated line to the [decision log](#decision-log). Examples: a supported version, a dependency or tool choice, a UX pattern, a security rule, a release or process step, or a preference the maintainer stated in a session.
2. **Edit, don't append contradictions.** When a decision is reversed, rewrite the rule where it lives, and change the old log line to say it was superseded and by what. No two lines of this file may disagree.
3. **Link, don't copy.** When the detail lives in a doc or in code, point to it. Copies go stale.
4. **Check it.** `test/agents.test.ts` fails when this file names a path that doesn't exist or an `npm run` script that isn't in package.json, when the Node.js version here doesn't match `src/node-check.ts`, or when `CLAUDE.md` stops importing this file. `npm run check` runs it.
5. **Before you finish a task,** reread the [decision log](#decision-log) and the sections you touched, and ask whether your change belongs in either. If the maintainer told you how they want something done, record it under [Working with the maintainer](#working-with-the-maintainer). A contributor's own preferences don't go in this file (see [Working with a contributor](#working-with-a-contributor)).

## What Keelson is

A self-hosted, **read-only** security posture tracker for **Cloudflare, Vercel, AWS, Alibaba Cloud, GitHub, GitLab and Gitea** (more providers, such as Google Cloud and Google Workspace, are planned). You give it a credential per platform (a token, an access key for AWS, an AccessKey for Alibaba Cloud, a GitHub App for GitHub, an instance's address and a token for GitLab and Gitea), and it scans daily. The web app lets you triage every finding until it is fixed. It ships only as a Docker image (`ghcr.io/r4reetik/keelson`), run on a laptop or for a team on a server, ECS or Kubernetes. It is open source (MIT) and published to GHCR from GitHub Actions; nothing is published to npm.

The name is for where it is going: beyond edge and network settings to code (GitHub organizations' settings and alerts are read today; the code itself is next), where that code is deployed and reachable from, cloud activity (CloudTrail, VPC flow logs), later runtime security, and an AI penetration tester that can work white box from all of that, or black box. None of this is built yet; design today's changes so it can be added.

**Sonar** (external attack surface) looks at each entity from the internet: the hostnames under its domains, the addresses they point at, and what is open there. Its first part is passive (certificate logs, public DNS and Shodan); checks Keelson runs itself are next.

It is built for many accounts, grouped into **entities**. An entity is a company, legal entity or team, and can hold accounts on several providers (its Cloudflare accounts, Vercel teams, AWS and Alibaba Cloud accounts together). Entities can be different companies, so their data, alerts and suggestions never cross. Each entity chooses whether it appears in the combined "All accounts" view (`includeInAll`). People may use one platform only: nothing may assume Cloudflare, or any other provider, is connected.

### Providers

- **Every account belongs to one provider** (`accounts.provider`; `src/shared/providers.ts` lists them). Everything provider-specific goes through the `Provider` interface (`src/providers/types.ts`), registered in `src/providers/index.ts`. The scanner, account routes and Add accounts flow never branch on a provider by name. How to add one: [CONTRIBUTING.md](CONTRIBUTING.md#adding-a-provider).
- **Nothing compares a provider's name.** What the app says about a provider comes from `PROVIDER_INFO` in `src/shared/providers.ts`: its label, its words for an account, a resource and a credential, the credential's fields, its API host, what its dashboard is called. The few per-provider pieces of UI and docs are records keyed by provider ID (`TOKEN_HELP` in `web/src/components/connect.tsx`, `PROVIDER_GLYPH` in `web/src/components/ui.tsx`, `SOURCE_REGISTRY` in `scripts/docs.ts`), so a new provider doesn't compile until it has an entry. Don't write `provider === "…"` anywhere, and don't write copy that lists providers by hand: use `providerList()`.
- **Layout.** New providers get `src/providers/<id>/` (client, sources, inventory, checks, catalog, engine, views, permissions), like `src/providers/vercel/` and `src/providers/aws/`. Cloudflare predates this and stays in `src/core`, wrapped by `src/providers/cloudflare.ts`; the engine, check format and categories in `src/core` are shared by all providers.
- **One check format, one engine.** Provider checks are written with `checksFor<Context, SourceKey>()` and summarised by `summarize()` in `src/core/engine.ts`. Categories are one shared list (`src/core/categories.ts`); add one only when no existing category fits. IDs carry a provider prefix (`V…` for Vercel, `A…` for AWS, `L…` for Alibaba Cloud, since `A…` is AWS's, `G…` for GitHub, `GL…` for GitLab (never `GLI`, which is GitHub's license check and older), `TE…` for Gitea) and are unique across providers. The full catalog is `src/providers/catalog.ts`.
- **A finding's `zone` is the provider's unit of grouping**: a Cloudflare zone, a Vercel project's name, an AWS or Alibaba Cloud region (or "Global" for IAM or RAM, S3 or OSS settings, CloudFront, CDN, Route 53 and Alibaba Cloud DNS), a GitHub or Gitea repository's name, a GitLab project's path below its group (none for a setting of the whole organization or group). Grouping, filters and links work the same for all of them; the UI names it from `PROVIDER_INFO.resource` (`zoneWord`).
- **Checks that span providers** (`XP-…`) compare an account with the other accounts in its entity through `links` stored in each scan's snapshot (`ProviderLinks`, `LINK_KEYS` in `src/shared/api.ts`) and passed as `related`. The scanner merges every list generically, so a new one needs no scanner change (name its publisher in `LINK_PROVIDER`). A scan leaves a list out when it couldn't read all of it, and a merged list is only used when every account of the publishing provider in the entity supplied it; otherwise it is null and named in `related.unknown`, so a check on the same provider can tell "no other account" from "another account we know nothing about". The checks never look outside the entity, and are skipped (not passed) when the entity has no scanned account on the other provider. See [docs/architecture.md](docs/architecture.md#checks-that-span-providers).
- **A view is a set of accounts**, named by a scope key (`src/shared/scope.ts`): `all`, `e:<entity>`, `a:<account>`, any ticked set `s:<id>,<id>`, and `@<provider>` to narrow one of the first two (`e:3@vercel`). Every scoped API, export, report and link follows the key. `keyForAccounts` gives a set its shortest key, so the whole of an entity is still `e:3`. A set may span entities only when all of them are shown in All accounts.
- **The two pickers are tick-box trees over that one set** (`ScopeSwitcher` and `ProviderSwitch` in `web/src/App.tsx`): entity → accounts, and platform → accounts. Ticking a parent ticks its accounts, the last account can't be unticked, and the menu stays open while ticking. There is no separate "all of this entity" row: the entity's own box is that. The platform picker shows only when the entities in view have more than one platform, and works for any number of platforms and accounts.
- **Scores:** each account is scored on its own checks; a view's score is the mean of its accounts' scores, and with several providers in view the Overview also shows each provider's mean (`providerScores`).
- **Provider-specific caches.** A provider keeps data between scans that doesn't belong in a scan's snapshot (GitHub's SBOMs) through `ScanInput.cache` (`provider_cache`, per account, removed with it), and scanners' own data (Grype's database) in `ScanInput.toolDir` (`<data-dir>/tools`).
- **Vercel API facts learned from a real team** (the OpenAPI description doesn't say them):
  - Managed rulesets (bot protection as `bot_filter`, `ai_bots`, `owasp`, `vercel_ruleset`) live on the project in `security.managedRules`, not in the firewall configuration. The firewall configuration holds custom rules, IP rules and the OWASP core ruleset (`crs`, per attack type).
  - A project that was never configured has no `security` block and its firewall configuration answers 404. Vercel's defaults apply: firewall on, managed rulesets off.
  - Someone invited appears both in `emailInviteCodes` and as a member with `confirmed: false`.
  - A token scoped to one team gets 400 from `/v6/user/tokens`; only a Full Account token can list tokens.
  - Team two-factor enforcement is `mfa.enforced` on the team.
  To check a shape against a real team, use a throwaway script that sends GET requests only and prints keys and counts, never values or the token.
- **AWS, as built** (checked against two real accounts on 2026-11-10: every source was readable and parsed; the Lambda function-URL and public snapshot and image answers had nothing in them, so those shapes are still from the API references only. The services added on 2026-11-15, in `services.ts`, are from AWS's API models and not yet checked against a real account):
  - Requests are signed GETs where the API takes them: the Query APIs (IAM, STS, EC2, RDS, load balancers, ElastiCache, Redshift, SNS) take their action in the query string; S3, CloudFront, Route 53, Lambda, GuardDuty, EKS, OpenSearch, MQ, MSK and EFS are REST. **Services whose APIs only accept POST** (CloudTrail, KMS, Config, ACM, Secrets Manager, ECR, ECS, DynamoDB, Cognito, WAF, Systems Manager, CodeBuild, EventBridge, SageMaker, SQS) are read with a signed POST through `rpc()`, and only for the actions in `READ_ACTIONS` (`src/providers/aws/client.ts`): each starts with Describe, List, Get or BatchGet, `rpc()` refuses anything else before sending it, and `test/aws.test.ts` fails on a POST for any other action. Add a read action to that list only after checking in the API reference that it reads; never a secret's value (`GetSecretValue`, `GetParameter` with decryption). Organizations is still unread.
  - Services that cost a request per item (keys, secrets, tables, repositories, task definitions…) are read up to `MAX_ITEMS` per region (`src/providers/aws/services.ts`). A service AWS doesn't offer in a region (its host doesn't resolve) reads as empty, not as a coverage gap (`readIn`).
  - Resource policies are reduced to conclusions in `src/providers/aws/policy.ts`: lets anyone in (`"*"` with no condition; any condition counts as narrowing, which can miss one that narrows nothing), the other accounts named, whether a bucket refuses plain HTTP, and privilege escalation paths. AS3-004 leaves out the accounts AWS uses to deliver load balancer logs.
  - Privilege escalation (AID-013) is judged from customer managed and inline policies only: AWS managed policies' documents aren't read, so one that allows `iam:PassRole` with `lambda:CreateFunction` isn't counted.
  - EKS's version status comes from AWS (`DescribeClusterVersions`), so no table of support dates goes stale. EKS secrets encryption isn't judged: AWS encrypts Kubernetes API data with KMS by default on current versions.
  - **Compared with Prowler (2026-11-15), AWS checks that aren't practical are left out on purpose:** compliance-only CIS metric filters and alarms, Multi-AZ, deletion protection and minor-version settings (availability, not security), copy tags to snapshots, X-Ray, password expiry (NIST advises against it), Shield Advanced and Security Hub, Macie or Inspector "is enabled" checks, encryption with a customer managed key where AWS's own encryption is on, S3 versioning, access logging and requiring HTTPS on every bucket, launch-wizard security groups, and checks that read data (CloudWatch log events, Lambda code). AWS Organizations and IAM Identity Center are next, with a decision on reading them.
  - No AWS SDK: `src/providers/aws/sigv4.ts` signs with `node:crypto` (tested against AWS's published example signatures) and `src/core/xml.ts` reads the XML answers.
  - The credential is one long-lived access key, stored in the vault as `<key ID>:<secret>`. A key belongs to one account, so `listAccounts` returns that one. Temporary keys (ASIA…) are refused; assuming a role into other accounts isn't supported yet. The key's user should have only AWS's managed SecurityAudit policy.
  - Regional sources are read in every enabled region. A region that refuses the key (a service control policy) is skipped and recorded (`skippedRegions`), not a coverage gap, unless every region refuses. A bucket that refuses is left out the same way.
  - Per-region settings (GuardDuty, EBS encryption by default, flow logs) are judged only where something runs, so empty regions and unused default VPCs don't produce findings.
  - Policy documents are reduced to what they allow and never stored; only the last four characters of an access key ID are kept. Start-up scripts (instances and launch templates) and environment variables (Lambda functions, ECS task definitions that a service runs, CodeBuild's plain-text variables) are scanned for credentials in memory with the shared patterns in `src/core/secret-patterns.ts` (`secretInVariables`), and only the variable's name and the kind found are kept; a variable only named like a secret is "likely". SNS endpoints keep only their host. `test/aws.test.ts` checks the stored data.
  - **Load balancer routing** (`lbRouting`, from 2026-11-16): application load balancers' listener rules (`DescribeRules`), the region's target groups (`DescribeTargetGroups`) and the targets registered in groups a load balancer uses (`DescribeTargetHealth`, at most 200 groups a region), all Query API GETs in SecurityAudit. Other load balancers route by their listeners' default actions; a classic one sends everything to its instances on the listener's instance port. A rule keeps its host and path values, and other conditions by kind only: a header condition keeps the header's name and never its value, which is often a shared secret (`test/aws.test.ts`). Each AWS scan publishes `awsLoadBalancers` (every load balancer with its routes down to the targets, each target's public address and whether its groups let anyone reach its port) and `awsExposure` (every public address with what has it and its inbound rules open to anyone), for Sonar.
  - A security group is judged by the network interfaces it is attached to (`DescribeNetworkInterfaces`), not by its rules alone: the check's own severity when something with a public address uses it, one step lower when only private interfaces do, low when nothing does.
  - AWS's public address ranges (`ip-ranges.amazonaws.com`, `src/core/aws-ranges.ts`) are read without the access key, by AWS scans and by a Cloudflare scan whose entity has an AWS account, to tell a DNS record that points at an AWS address from one that points elsewhere.
  - **An exposed origin is rated by its security groups.** Each AWS scan publishes `awsOrigins` (load balancer DNS names and public interface addresses, each "open", "cloudflare" or "other" for ports 80 and 443, with the groups' names and IDs; the ranges themselves aren't kept), and Cloudflare's ATS-001 reads it: critical (high with an origin lock) when open, low when only Cloudflare's ranges (`src/core/cloudflare-ranges.ts`) and private ones are admitted, medium when other public ranges are. Managed prefix lists in web rules are read (`GetManagedPrefixListEntries`, in SecurityAudit) and their entries count like any other range. An origin with a prefix list that couldn't be read, no groups of its own (a network load balancer) or no web rule isn't listed, and keeps ATS-001's rating without AWS. ATS-001 and XP-006 name each other in their evidence; `corroborated` is only for Security Center insights.
  - **A dangling record is rated by what can be done with it** (`DANGLING` in `src/core/links.ts`): a missing S3 bucket or CloudFront alias can be claimed (high); a missing load balancer can't, because its name is random (low). An AWS address is only called dangling when Keelson saw it leave the entity: each AWS scan carries an `addressHistory` (held now, released since) from the previous snapshot, passed in as `ScanInput.previous`. An AWS address nobody in the entity ever held is a low-severity note, because on real accounts most of those were vendors' servers and accounts that weren't connected.
  - A role's trust policy keeps, besides who may assume it, only the GitHub subjects (`token.actions.githubusercontent.com:sub` under a String… operator, lowercase) when GitHub's OIDC provider may assume it. AID-012 needs only those; XP-010 and XP-011 compare them with the entity's GitHub organizations and repositories. A role limited to a GitHub environment isn't judged until environments' rules are read.
  - Things AWS owns on the account's behalf aren't in the account's own lists and look like dangling records if they're missed: classic load balancers (an older version of the load balancer API) and the CloudFront distributions behind API Gateway custom domains. Both are read. Expect more of these (Cognito, Amplify, AppSync); dangling-record findings stay "likely".
- **Alibaba Cloud, as built** (from Alibaba Cloud's OpenAPI metadata, `https://api.aliyun.com/meta/v1/products/<Code>/versions/<version>/api-docs.json`; first checked against the maintainer's real account on 2026-11-17, see the last points below):
  - **Every request is a signed GET**, signed by `src/providers/alibaba/sign.ts` with `node:crypto` (no SDK): V3 (ACS3-HMAC-SHA256) for the RPC and ROA APIs and OSS's V4, tested against Alibaba Cloud's worked V3 example and the OSS Go SDK's test vectors; the mock signs each request again and refuses a mismatch. Alibaba Cloud's RPC APIs accept GET for changes too, so `rpc()` and `roa()` send only actions that start with Describe, List or Get **and** are in `ALIBABA_ACTIONS` (`src/shared/alibaba.ts`); `test/alibaba.test.ts` fails on any other. Add an action there only after checking in the API metadata that it reads, and never one that returns data or a secret (`oss:GetObject`, `kms:GetSecretValue`, `cs:DescribeClusterUserKubeconfig`, `fc:GetFunctionCode`, `sae:DescribeNamespaces`, which returns an AccessKey). The policy also holds `cr:PullRepository` (`ALIBABA_DATA_ACTIONS`), which no API call uses: it lets Trivy pull images to scan (see [Container images](#container-images)).
  - **The credential is a RAM user's AccessKey with a custom policy that names exactly those actions** (`alibabaPolicy()`, shown ready to paste in Add accounts). There is no system policy like AWS's SecurityAudit: `ReadOnlyAccess` and the per-product read-only policies use `Get*`, which includes `oss:GetObject` and (outside KMS's own policy) `kms:GetSecretValue`. The vault stores `<AccessKey ID>:<secret>`; STS tokens are refused. Account IDs are the 16-digit UID.
  - The main account's AccessKeys and MFA come from IMS's `GetAccountSecurityPracticeReport` (`RootWithAccessKey`, `BindMfa`), readable by a RAM user; an account under a day old has no report yet, and nothing is judged. Keelson scanning with the main account's own key is always reported.
  - RAM users are read through IMS (`ims.aliyuncs.com`, whose RAM actions are `ram:…`), which gives each user's last sign-in as a millisecond timestamp and their UserPrincipalName for `GetAccessKeyLastUsed`. ACK's `DescribeClustersV1` is the RAM action `cs:GetClusters`; Security Center's actions are `yundun-sas:…`, at `tds.cn-shanghai` for the China site and `tds.ap-southeast-1` for the international one, so both are asked. Function Compute 3.0 is at `fcv3.<region>`.
  - Regional reads go to `<product>.<region>.aliyuncs.com`; ECS, VPC, SLB and RDS, which take `RegionId`, fall back to their central endpoint where the regional one doesn't resolve. A product that isn't offered in a region or that the account never opened reads as empty, not as a gap; a region that refuses is skipped (`skippedRegions`), like AWS's.
  - **Security groups have priorities and drop rules**: an accept rule from anywhere is left out when a drop rule from anywhere with the same or higher priority covers it (`toSecurityGroup`). Groups are judged by what they are attached to, as on AWS. A CLB has no security groups and no DNS name: it is matched by its address.
  - **OSS dangling records are medium, not high**: a deleted bucket's name is free after a few hours, but OSS only serves a custom domain from a bucket once its owner proves they control the domain (a TXT record, or the domain in their own Alibaba Cloud DNS), so what a squatter gets is links to the bucket's own address. Load balancer names carry random IDs, and CDN asks for domain proof, so those are low.
  - Policy documents (RAM and OSS) are reduced in `policy.ts` and never stored; a bucket policy's other accounts are counted only for 16-digit IDs and `acs:ram::<uid>:` ARNs, since RAM user IDs are numeric too. Function Compute environment variables, instance user data and launch templates are scanned in memory; `DescribeDBInstanceSSL` returns the server's private key and only `SSLEnabled` is read; an ALB header condition keeps only the header's name.
  - Each Alibaba Cloud scan publishes the same lists as AWS under `alibaba…` names (`alibabaEndpoints`, `alibabaAddresses`, `alibabaReleased`, `alibabaAccounts`, `alibabaOrigins`, `alibabaLoadBalancers`, `alibabaExposure`) plus `alidnsZones` and `alidnsDns`, in AWS's shapes (`AwsLoadBalancerLink.provider` says which cloud), so Cloudflare's ATS-001, Sonar's routing and the dangling-record checks read both clouds with the same code. Cloudflare publishes `toAlibaba`.
  - **Compared with Prowler (2026-11-17), Alibaba Cloud checks that aren't practical are left out on purpose:** the CIS Log Service alert rules (`sls_*`), Security Center's paid editions, notification and vulnerability-scan settings, PostgreSQL logging parameters, SQL audit and its retention, a customer key for TDE, ACK cluster checks, dashboard, RBAC and log settings, OS patch level, policies attached to users rather than groups, password expiry, and versioning, logging, encryption and HTTPS-only on every OSS bucket. Tair (Redis) and MongoDB are read since 2026-11-17 (whitelists, public endpoints, password-free access, TLS); WAF, Cloud Firewall and Resource Directory are next.
  - **Checks are judged the way Alibaba Cloud works, not copied from AWS** (2026-11-17): an ApsaraDB whitelist, not a security group, decides who connects, so a whitelist of 0.0.0.0/0 is critical only with a public endpoint, and TLS off is low inside the VPC. Tair and MongoDB can let VPC clients in without a password (LDB-004); their `VpcAuthMode` means opposite things (Tair: `Close` is password-free; MongoDB: `Open` is), and `test/alibaba-checks.test.ts` reads both through the mock. A CLB has no security group and its backends must admit its addresses (100.64.0.0/10), so a CLB listener on an admin or database port without a whitelist ACL is exposure the groups don't show (LNW-005; ACLs come from `slb:DescribeLoadBalancerListeners`, its own source `lbAccess`). ECS disks aren't encrypted unless asked, and the setting is per region, so it is one finding per region, not per disk. MFA is judged with RAM's security settings (`GetSecurityPreference`): when MFA is required at sign-in, a user without a device binds one at the next sign-in, whoever makes it, so it is one step lower, not a pass. Users who manage their own AccessKeys (LID-014) and users used by a person and by programs at once (LID-015, Alibaba Cloud's own advice) are checked. A Linux instance without a key pair, on a public address with port 22 open, signs in by password (LEC-009, "likely": sshd may refuse passwords). A public-read bucket is high; anyone writing, or the audit log in it, is critical, and one that Alibaba Cloud CDN serves is told the CDN can read a private bucket. Container Registry's own buckets (`cri-…-registry`) aren't judged for Block Public Access.
  - **Alibaba Cloud has its own inventory page, Resources** (`web/src/pages/Resources.tsx`, `/api/resources`), not AWS's Regions page: its regions (about thirty, most empty) and products differ, and rows of region counts said little. Each scan stores `resources` (`ResourcesView`, `resourceView()` in `views.ts`): one row per resource in Alibaba Cloud's words (ECS instance, CLB, ALB, NLB, OSS bucket, RDS, Tair, MongoDB, function, ACK cluster, VPC, security group, RAM user and role, CDN and DNS domain), how the internet reaches it, the facts the checks read, and its open findings, matched by zone and ID; regions only as a filter, with their English names (`DescribeRegions` with `AcceptLanguage=en-US`). Service-linked roles are left out.
  - **Learned on the maintainer's real account (2026-11-17):** `DescribeInstanceRamRole` takes at most 50 instances and `PageSize` 50 (100 failed every region with instances, and skipped every instance check). In the local regions (cn-fuzhou, cn-nanjing, cn-wuhan-lr) the ALB and NLB hosts resolve to a shared gateway that answers 403 "The specified region of  is not authorized." for a product that isn't offered there: it is read as "not offered" (`NOT_OFFERED` in `client.ts`), not a missing permission. Sold-out regions still run instances and are read. Function Compute 3.0's endpoint in a region it isn't offered in (ap-southeast-6) resolves and answers every request with 503: a 503 on a region's first list is "not offered"; any later failure stays a gap. Elastic Container Instance answers 400 "The specified parameter RegionId:cn-fuzhou is not valid" in a region it isn't offered in (2026-11-19), also "not offered": as a gap it left every container group, and so every running image, unknown. Thirty-three "all traffic from anywhere" findings were on the security groups of ALBs and NLBs (`ALB_SYSTEM_SECURITY_GROUP-…`, attached only to interfaces Alibaba Cloud manages): a group used only by load balancers or services exposes their listeners, which LNW-005 and the TLS checks judge, so the port checks pass it (`isServer` in `checks/define.ts`); identical rules that differ only in what isn't kept are read once. A coverage gap names the endpoint that failed, so a region's 5xx can be told from a missing permission. The account had 16 public-read buckets, 148 unencrypted disks (one low finding each before they were folded into their regions), and a RAM role whose GitHub trust uses GitHub's immutable subjects (`repo:<owner>@<owner ID>/<repo>@<repo ID>:…`, the default for repositories created from July 2026), which XP-022 read as an outsider until `withoutIds()` in `src/core/github-trust.ts` (shared with AWS) dropped the IDs.
- **GitHub, as built** (from GitHub's REST reference, `https://docs.github.com/rest`, and not yet checked against a real organization):
  - **The credential is a GitHub App the user registers and owns**, not a personal access token: it isn't tied to a person, each organization's owners see and control it, one App covers every organization it's installed on (`listAccounts` lists the App's installations on organizations; ones on personal accounts aren't offered), its rate limit grows with the organization, and it is the base for webhooks later. Classic personal access tokens can't be read-only; fine-grained ones can, and could be added later as a simpler option, since the reads are the same.
  - The vault stores `<App ID>:<private key>`. A one-line input drops the key's line breaks, so `normalizePem` in `src/providers/github/client.ts` rewraps it; the credential hint on the Accounts page is the App ID (`maskToken`), since a key always ends in `-----`. Account IDs are `gh_<organization number>`, so they can't be mistaken for AWS's 12 digits.
  - **The one POST:** each scan signs a JWT with `node:crypto` (no Octokit) and asks `POST /app/installations/{id}/access_tokens` for a token with **read** on Keelson's permissions (`GITHUB_APP_PERMISSIONS` in `src/shared/github.ts`) that the installation was granted, and nothing else. That token can do less than the App, even when the App was given write. Every other request is GET; `test/github.test.ts` fails on any other POST, or a token request that asks for more than read.
  - The App registration link (`githubAppTemplate`) pre-fills Keelson's read permissions, no webhook, and a name with the organization in it, since App names are unique across GitHub.
  - Secret scanning alerts are read with `hide_secret=true` and the `secret` field is dropped anyway; webhook URLs keep scheme and host; deploy keys keep title and access.
  - **Contents is asked for, for dependency files only** (from 2026-11-16). With it, each scan lists the default branch's files (`git/trees`) and fetches, by blob SHA, only the files `wanted()` picks in `src/core/sbom/manifests.ts`: package manifests and lock files, GitHub Actions workflows and Dockerfiles, outside installed packages, build output and test fixtures. Source code is never fetched (`test/github-dependencies.test.ts` checks that a source file in the mock is neither requested nor stored). The files go to a temporary folder for Syft and are deleted; only the SBOM's packages, the parts Keelson read from the files, the actions workflows use and npm's development-only package names are kept. An App without Contents makes `manifests` a coverage gap and nothing is listed: public repositories would still answer, but a partial inventory would pass checks on what wasn't read.
  - **Dependencies (SBOM) come from Anchore's Syft, Grype and Grant** (`src/core/anchore.ts`), run when installed: `KEELSON_SYFT`, `KEELSON_GRYPE`, `KEELSON_GRANT` (a path, or `off`), else the tool on the PATH. The Docker image carries all three (from 2026-11-23): release archives pinned by version and SHA-256 sum for each platform in the Dockerfile, which a test checks; Dependabot doesn't update them, so a newer release is a hand change of its version and both sums. Each runs with only the PATH, a temporary home, proxy variables and its own settings, which keep Syft and Grant offline (no registry lookups for licenses: they would send private package names to public registries). Grype's database (about 3 GB) lives in `<data-dir>/tools/grype` and is refreshed from Anchore. Missing tools are coverage gaps (`syft`, `grype`, `grant`), like Amass; what such a gap needs is worded from `src/shared/tools.ts` for how this copy runs (`Session.install`), never from the text its scan kept, and never blamed on the platform or its credential. The mock (`dev/mock/anchore.ts`) replaces them, so tests never run the real ones.   - **An SBOM is made again only when a picked file changes** (its path, its blob SHA, or Syft's version): it's kept in `provider_cache` (`sbom:<repo>`, gzipped JSON, removed with the account), so most scans send one tree request per repository. Grype runs every scan, once over the unique packages of every repository (by type and purl), so new advisories are found in unchanged code.
  - **A repository's parts are found from its files, not from Syft**: each folder with a manifest, lock file or Dockerfile is a part (a monorepo's projects), a workspace without a lock file of its own takes the nearest one above it in the same ecosystem, and folders such as `examples/` and `test/` are development only. A package is attributed to the parts whose manifest names it (direct), the parts that reach it through Syft's `dependency-of` graph, or the part holding its lock file.
  - **Dependency findings are one per package and repository, whatever the version** (resource `name (ecosystem)`), so triage survives an upgrade that's still vulnerable. A package with a vulnerability in CISA's KEV catalog is GDP-001 (critical), one with a critical or high vulnerability, or any with EPSS of 10% or more, is GDP-002 at its worst severity; known malware (OSV `MAL-` IDs) is GDP-003. Development-only packages are one step lower, and so is a package that only other packages use when none of its listed vulnerabilities has an EPSS of 1% or more (`EPSS_LIKELY`); known-exploited ones are never lowered. Matches by CPE alone are "likely". Medium and low vulnerabilities unlikely to be exploited show on the repository's page but aren't findings. An advisory and its CVE are one vulnerability (`mergeAliases`), with the smallest fixing version.
  - **The Dependencies page** (`web/src/pages/Dependencies.tsx`) works across every repository in the view: `src/server/sbom.ts` builds an index from the cached `deps:<repo>` views once per account and scan, joins triage on every request, and filters and pages on the server (`/api/sbom`, `/api/sbom/packages`, `/vulnerabilities`, `/licenses`, `/packages.csv`), since an organization has tens of thousands of packages (17,380 unique on the maintainer's). Filters live in the URL; a language filter groups package managers by the language they're for (`languageOf` in `src/shared/dependencies.ts`), since the maintainer looked for packages by language and found only package managers. Picked rows, or every row that matches, give the repositories they affect as `owner/repo` with links, the IDs and the upgrades to make (`affectedRepos` in `src/server/sbom.ts`), because the maintainer needed to tell the owners of every repository a vulnerable package is in. Its Licenses tab is the Grant report: the maintainer couldn't find where Grant's results were, so licenses have their own tab and each repository's page its own summary.

  - GDP-004 (actions used by a tag) leaves out actions owned by GitHub (`actions/*`, `github/*`) and the organization itself. GDP-005 (no lock file) is limited to the kinds of projects that normally lock: npm, Composer and Bundler projects, Go modules, Pipenv and Poetry projects and requirements files with versions that aren't pinned; libraries' pyproject dependencies and Rust crates aren't judged. GLI-001 (strong copyleft) is skipped when the repository's own license is a copyleft one, and is medium for AGPL and SSPL. A Composer package below the repository's root is judged only when its `type` is `project`: Composer's default type is a library, and copies of libraries inside an application (CodeIgniter's `application/libraries`) don't lock.

Grant 0.7 prints only a count with `-q`, so it runs without it, and every tool's output is checked for the list Keelson reads (`report()` in `src/core/sbom/index.ts`): anything else is a coverage gap, never an empty result. An installation token is cached per set of granted permissions, so a permission the organization accepts later is used on the next scan. Lock files rarely state licenses except npm's, so GLI-001 sees mostly npm packages.
  - Archived repositories keep only what they are; empty ones aren't judged on branches. Branch protection counts classic protection and rulesets (the repository's and the organization's, read from `/rules/branches/{branch}`) alike (`branchGuard`).
  - Secret scanning off is only reported on public repositories, where it's free; on private ones it needs a paid GitHub product, and the check would fire on most of them. Dependabot and code scanning findings count critical and high alerts only.

Learned on the maintainer's real organization (2026-11-14), where secret scanning was off on all 324 repositories and every one passed "no leaked secret". A private repository without GitHub Code Security answers 403 on analyses, which means "not set up", not a missing permission.
  - On the same organization, "Dependabot security updates off" fired on every repository, so it is limited to repositories with open Dependabot alerts; an unreviewed default branch is low severity after a year without a push.
  - **Self-hosted runners are judged from public repositories' side** (`publicRunners` in `src/providers/github/checks/actions.ts`): a runner group open to public repositories reaches the ones it lists (or all), plus each public repository's own runners. It is critical only when a runner isn't ephemeral and the fork pull request approval policy lets some outside contributors run without approval; a group limited to named workflows is medium. This needs the App's **Self-hosted runners** organization permission, added on 2026-11-15; an App registered earlier reports it missing and the check is skipped.

The fork pull request policy (`/actions/permissions/fork-pr-*`) answers 404 on plans that don't offer it, which is "nothing to judge", not a gap.

CODEOWNERS and SECURITY.md files, code owner review and workflow analysis (zizmor-style) wait for reading code (the Contents permission).

### Container images

- **Images are followed from the repository that builds them to what runs them.** AWS, Alibaba Cloud and GitHub scans list their registries' images, scan the ones that matter with Aqua's Trivy, and publish what they know to the entity: workloads that run images (`awsWorkloads`, `alibabaWorkloads`, in the `WorkloadLink` shape with how the internet reaches each) and the images GitHub workflows push (`githubImageBuilds`). Everything shared is in `src/core/images.ts` (which images, the scan, what is kept), `src/core/trivy.ts` (the runner), `src/core/kev.ts` (CISA's list), `src/core/eol.ts` (runtimes' support dates), `src/core/image-index.ts` (what is in which image, compactly), `src/core/image-checks.ts` (the checks) and `src/shared/images.ts` (the shapes, and how references are read). A new platform with a registry or container workloads lists them in those shapes and calls `pickImages`, `scanImages` and `reportImages`; it writes no scanning or check logic of its own. How it works end to end: [docs/architecture.md](docs/architecture.md#container-images-from-the-repository-to-what-runs).
- **Pulling an image is the maintainer's decision, and the one place Keelson reads data rather than configuration** (2026-11-18). It needs permissions SecurityAudit and Keelson's Alibaba Cloud policy didn't have: `ecr:GetAuthorizationToken`, `ecr:BatchGetImage` and `ecr:GetDownloadUrlForLayer` on AWS (an inline policy; AWS's AmazonEC2ContainerRegistryPullOnly also allows `ecr:BatchImportUpstreamImage`, a write, so it isn't suggested), and `cr:GetAuthorizationToken` with `cr:PullRepository` on Alibaba Cloud (`ALIBABA_DATA_ACTIONS` in `src/shared/alibaba.ts`: in the policy, never an API call the client sends). Each is optional: without it the images are listed and `imagePull` is a coverage gap. Don't extend this to other data (objects, function code, secret values).
- **Trivy gets a registry login that expires within hours, for one registry host, and nothing else.** The login (ECR's 12-hour token, Container Registry's one-hour temporary user) is written to a Docker configuration file for that run, keyed to the image's registry host, and deleted after. Never pass it through `TRIVY_USERNAME` and `TRIVY_PASSWORD`: Trivy offers those to every registry it contacts, the ones its database comes from included. The child gets `AWS_EC2_METADATA_DISABLED=true`, so Trivy's own ECR code can't borrow the role of the machine Keelson runs on, and both the version check and telemetry are off (Trivy sends them in one request, skipped only when both are). The access key, AccessKey or App key never reaches it. `test/images.test.ts` runs the real runner against a stand-in script to check all of this.
- **Only what was concluded from an image is kept.** Packages, vulnerabilities, the operating system and whether it is past its end of life, the user, the build date, the start of each layer's ID, and the source repository, revision and base image labels (a source URL keeps host and path only: it can carry a token). One kind of variable is read for its value: the ones official images record their runtime's version in (`NODE_VERSION`, `NGINX_VERSION`… `RUNTIMES` in `src/core/images.ts`), and only a version number is taken from it. A credential Trivy finds in a file keeps its kind and the file's path; the image's environment variables and build history are scanned in memory with the shared patterns (`secretInVariables`, `secretKindIn`) and only the kind is kept. Trivy's report holds the variable values, the lines around a secret and every label: `reduceReport` never copies them, the bill of materials kept for matching again is written from the report's packages alone, and `test/images.test.ts` checks the stored data. Elastic Container Instance groups come back with their containers' variable values, dropped as they're read.
- **An image pushed as an index is one image.** A build for several platforms, or with build attestations (Docker's default), is pushed as an index; ECR lists the index under its tag and each part as an untagged image of its own, pulled whenever the index is. An AWS scan reads each index's manifest (`ecr:BatchGetImage`, which returns JSON that names the parts, never a layer; `foldIndexes` in `src/providers/aws/images.ts`), drops the parts from the list and keeps the platforms. Trivy asks for linux/amd64 by default, so an index without it is asked for by a platform it has, and on any registry "no child with platform" is retried once as linux/arm64. What Trivy says isn't an image (an attestation) is dropped from the list and remembered, so it isn't asked for again.
- **Which images are scanned** (`pickImages`): every image a workload in the entity runs, images pulled in the last 30 days (ECR records it; something runs them that Keelson can't see, such as a Kubernetes cluster), the newest three of each repository (`PULLED_PER_REPOSITORY`: a repository deployed daily has dozens pulled within the month, and only the last few still run), and the newest image of each repository, most exposed first, at most 400 a scan. A registry holds every build ever pushed, so the rest are not listed at all. An image is scanned by the account whose registry holds it; one a workload runs from a public registry by the account that runs it, without a login; one in a private registry no connected account holds is listed as unreadable, not tried.
- **Scanners' databases are updated by scans, and on request from Settings** (`src/scanner-tools.ts`, `Scanner.tools`, `GET /api/scanners`, `POST /api/scanners/<grype|trivy>/database` with the `settings` permission). Grype checks for a newer database each time it runs and Trivy before each scan that reads images; Settings → Scanners shows each scanner's version and each database's build date and starts an update in the background. Every Grype command on its database takes its turn (`grypeInTurn` in `src/core/anchore.ts`), as Trivy's do (`inTurn`), so an update never replaces a database a scan is reading. Which scanners have a database Settings can update is `database` in `src/shared/tools.ts`.
- **A scan must not take the machine it runs on.** Every scanner Keelson runs (`runChild` in `src/core/anchore.ts`: Syft, Grype, Grant, Trivy) gets the lowest process priority and `GOMAXPROCS` of half the cores, at most four (`scannerCpus`); Trivy also gets `--parallel` to match and a soft memory ceiling (`GOMEMLIMIT`, a quarter of the machine's, at most 2 GB). During a scan only what the checks read of each image is held in memory (`ImageHighlights`), never every package of every image. The maintainer runs Keelson on a laptop, where Trivy on every core made everything stutter for as long as a scan ran.
- **Scans are one image at a time, and a scan always reads what matters most itself** (`trivyLimits`, `readInScan`): Trivy's cache takes an exclusive lock, so two processes can't share it, and every command that opens it waits its turn (`inTurn` in `src/core/trivy.ts`). The images workloads run and each repository's latest image are read by the scan, however long that takes: about half a minute for an image never read before, so the first scan of a registry with hundreds of repositories takes hours, and later ones seconds. The others (a repository's older builds that were pulled lately) get what is left of 30 minutes; the ones not reached are counted (`waiting`) and handed back as a backlog (the next point). The order is by what a scan adds (`inScanOrder`, from the previous scan's snapshot): what a scan reads itself, never read before read; then the rest, never read and then from the one read longest ago; in listed order a large registry's first images were read again every day and the others never reached. When a registry has more than `MAX_IMAGES`, what a scan reads itself is kept before older builds. Each image's result is kept in `provider_cache` (`img:<registry>/<repository>@<digest>`), and CISA's list is applied again on every scan. Trivy's database is updated first, on its own (`--download-db-only`), so no login is around while it downloads. Only pulling counts against the 30 minutes: matching a stored image again (the next point) is done for every image, whatever time is left.
- **What a scan had no time for is read in the background, and the account is then scanned again** (`ImageBacklog` in `src/core/images.ts`, the worker in `src/scanner.ts`). A scan returns its unread images as `ScanOutput.backlog`. Once no scan is running or queued, the scanner reads each account's backlog one image at a time, with that scan's registry access (a login is asked for again every half hour), and writes each result to the account's cache. When an account's backlog is done and at least one image was read, the account is scanned again (trigger `images`): that scan pulls nothing, and it is what gives those images their findings, their alerts and their rows on the Images page. Nothing of a finished scan is changed. A scan that is asked for always goes first: the background gives way after the image it is on. The top bar shows it like a scan's progress (`ScanStatus.background`), only to users who can see the account, and the shell asks for it every ten seconds, not two. A backlog lives in memory: after a restart the images wait for the account's next scan, which hands back what it still can't reach. The mock dev server shows all of this on the first scan of its AWS account.
- **An image is pulled once.** One named by its digest never changes, so what Keelson read from it (packages, credentials, layers, runtimes) stays true and only what Trivy's database says of its packages can change. After a pull, Trivy writes its own bill of materials for what it read (`trivy convert`, from the report's packages only: `inventoryOf`), and Keelson keeps it beside the result (`imgsbom:…`, `keptSbom`: the components and their dependencies, without Trivy's description of the image, where it would put every label, and without its list of vulnerabilities). Every later scan gives that to `trivy sbom`, which matches it against the current database without contacting anything, and replaces the result's vulnerabilities and the operating system's end of life (`rematched`); `scannedAt` stays when the image was read, and `dbUpdated` says which database its vulnerabilities are from. A result matched against the same database isn't matched again. Trivy's own CycloneDX is used rather than one written from Keelson's packages because it carries what matching needs and Keelson doesn't keep (a Debian package's source package, each package's layer). An image is pulled again only when it has no stored bill of materials (scanned before 2026-11-19, or Trivy couldn't write or match it), when `IMAGE_FORMAT` changes, or when it is named by a tag alone and was read more than 20 hours ago (the tag may have moved; Trivy fetches only layers it hasn't read). A newer Trivy doesn't pull images again. Checked with the real Trivy on three public images (2026-11-19): the same vulnerabilities as the pull, with their layers, in under a tenth of a second per image against half a minute for a pull. Each scan's snapshot says how many images it pulled and how many it only checked (`pulled`, `checked`), shown under the Images page's tabs. On the maintainer's real registry the same day, a scan pulled 70 images it had never read in its 30 minutes and pulled none of the 78 the scan before had read; matching a real registry's images against a newer database wasn't seen yet, since the database hadn't changed between the two scans.
- **Trivy's report has no EPSS and no known-exploited flag**, so Keelson reads CISA's catalog itself (`src/core/kev.ts`: one public file, once a day, kept in the tool folder). EPSS isn't read for images.
- **A runtime an official image installs from a tarball is in no package list** (Node.js in `node`, Python in `python`), so Trivy matches nothing to it. Keelson reads its version from the image and asks endoflife.date whether its release line still gets fixes and what its newest release is (`src/core/eol.ts`: one small public file per product, once a day, only the product's name sent). It is an indication of support, not a list of CVEs, and is applied again on every scan like CISA's list.
- **The base image is told from the build history.** A base image ends with its own CMD line, which adds no layer, and the build's steps come after: the layers before the last such line that still has a layer after it are the base's (`baseLayerCount`, the way Trivy tells them apart). Each package and vulnerability says whether its layer is one of them (`base`). The base's name comes from the image's own label (`org.opencontainers.image.base.name`), else from the FROM lines of the Dockerfiles in the repository that builds it, and an image whose layers start with every layer of another scanned image of the entity is shown as built on that one.
- **Four checks, defined once** (`imageCheckMeta`, `reportImages`), under each platform's prefix (`AIM-`, `LIM-`, `GIM-`): a known exploited vulnerability, critical or high vulnerabilities with a fix, an operating system or runtime past its end of life, and a stored credential. One finding per image repository, whatever the tag, so triage survives the next build. Vulnerability findings are only for images in use, rated by exposure (`ImageUse`): internet-facing gets the check's severity, running inside the network one step lower, pulled lately one step lower and "likely". Vulnerabilities without a fix don't make a finding (a Debian image carries dozens nobody can act on), and stored-only images show on the page without findings. A stored credential is a finding wherever the image is, critical when anyone can pull it.
- **A workload is internet-facing by what Keelson can read**, never assumed: an ECS service behind an internet-facing load balancer whose rules forward to its target group (through a network load balancer that targets an application one too), or with a public address and a security group rule open to anyone; an ECI group with a public address in a group open to anyone; a Function Compute function with an anonymous HTTP trigger. Tasks on their instance's network are "can't tell" (null), not "no".
- **Who builds an image** has three sources and a fallback, shown as such: the image's own `org.opencontainers.image.source` label (docker/metadata-action writes it; docker/build-push-action alone doesn't), the repository a GitHub package is linked to, and a workflow that pushes an image of that name (`src/core/sbom/builds.ts`, a reading of text: `images:` and `tags:` of the Docker actions, `docker build -t`, `docker tag` and `docker push`, with the file's own variables filled in). A registry that comes from a login step, a secret or a repository variable is unknown, and the image is then matched by its repository's name within that kind of registry. Workflows are read from the SBOM's cached files; an SBOM cached before this fetches only its workflows again. When none of the three says, the one repository of the entity with the image repository's own name is taken ("prod/payments" and "payments-staging" are built from "payments"), and none when two share the name: pipelines outside GitHub Actions leave no other trace.
- **Where a vulnerability is fixed** (`fixPlaces` in `src/server/images.ts`, on the image's page, never stored): a package in a layer the base image brought is the base image's, whatever kind it is; an operating system package the image's own build installed is that build's; an application package is looked up in the dependencies of the repository that builds the image (`deps:<repo>`): still vulnerable there is "in the code", fixed there is "rebuild", absent there is "image build". Without the repository's dependencies it is only "application", and when the history doesn't show where the base ends, an operating system package is taken to be the base's.
- **Each image has a software bill of materials** (`src/server/image-sbom.ts`, `GET /api/images/sbom`): CycloneDX 1.6 with its vulnerabilities, or SPDX 2.3, written from what the scan kept rather than by running Trivy again. The Components tab is the same inventory across every image: each package, runtime and operating system at each version, with how many images hold it.
- **The Images page joins inside one entity** (`src/server/images.ts`): images come from the accounts in view, but the workloads, builders and DNS records they are joined with come from every account of their entity, so a view of one account still shows where its images run. Never across entities (`test/images.test.ts`). A view is built once per set of scans (told by their IDs, without reading a snapshot) and kept until one changes; triage is joined on every request.
- **Every list of the Images page is paged on the server, 50 rows at a time, and a row carries the first three of the images or workloads it names** with a count; a selection asks for its rows in full (`full=1`, `key=`). The lists across images read each account's compact index (`imgindex`, written by the scan; made once by the server for an account scanned before it existed), never every image's full result. **A search never goes through every image again** (`vulnRows`, `componentRows` in `src/server/images.ts`): the list without the search is made once per view and filter, a component search only picks rows from it, and a vulnerability search takes the rows whose own ID or title matches from it and looks up only the others, in the packages whose name matches. The one list that takes long to make (every vulnerability of every image, about a second on a real registry) is made in slices of ten milliseconds, so the server answers other requests meanwhile, and a search whose request the browser dropped stops at its next slice (`inSlices`, `Abandoned`); the list without a search is shared by the requests that wait for it and never dropped half made.
- **Not read, on purpose or not yet:** Kubernetes workloads (EKS, ACK) live in the Kubernetes API; Lambda functions built from an image need `lambda:GetFunction`, which SecurityAudit doesn't grant and which also returns a link to download a function's code; Container Registry Personal Edition has no API; App Runner and SAE are next. **GitHub's registry refuses a GitHub App's installation token for private packages** (GitHub's documentation and community reports through 2026, whatever permission the App has), so private packages are listed with who builds them and where they run, and not scanned; public ones are pulled without a login. Listing an organization's packages needs no App permission by GitHub's REST reference. Container Registry is not yet checked against a real account; ECR and GitHub were on 2026-11-19 (below).
- **Learned on the maintainer's real registries (2026-11-19):** two AWS accounts listed 800 images in 593 repositories, 786 of them "pulled lately" with only 31 workloads Keelson reads (the rest run on Kubernetes). A hundred of the 800 were build attestations and 241 were untagged parts of indexes, which is why indexes are folded; 32 images were arm64 only. 174 of 378 scanned images held a credential in a file (Helm values files, config maps, key files, a Jenkinsfile), so AIM-004 is the check that found most. One image in 800 carried a source label and no workflow pushed any (the builds run outside GitHub Actions), which is why the builder falls back to the repository's name. GitHub answered 400 "Invalid argument" to an installation token listing the organization's container packages, though its reference says it may: that answer (and 403, 404, 422) is "GitHub doesn't list packages for an App here", not a coverage gap, and the organization's images are then known only from the workloads that run them. The page drew all 800 rows at once (33,000 elements, drawn again every two seconds while a scan ran) and one page of vulnerabilities was 900 KB; the server held every image's full result in memory, about half a gigabyte. One repository had 86 images pulled within the month, and a scan's 30 minutes went on refreshing the images listed first, which is why a repository keeps its newest three and a scan starts with what it never scanned. With all of this, one account's scan read 363 images without an error or a coverage gap (one of them arm64 only) and reached 210 in its 30 minutes; 154 carried a runtime Keelson reads (Node.js, nginx, Python), six runtime versions and four operating system versions were past their end of life, the base image's layers were told apart in 153, and none named its base image in a label. An account's results showed only when every queued account was done, over an hour later, so the shell now refreshes the pages as each account of a queue finishes.
- **A registry host Keelson can't connect to is tried once a scan** (`TrivyError.unreachable`, from Go's "dial tcp … operation timed out", "connection refused" or "no such host"): its other images get the same error without asking Trivy, and it is a coverage gap of its own (`registryNetwork`, the `network` image source), not `imagePull`, since no permission fixes it. A provider can add what its registry's settings say about who may connect (`pickImages`' `reach`). Learned on the maintainer's Alibaba Cloud account (2026-11-19): a Container Registry instance's internet access had an allowlist, every pull timed out after minutes of Trivy's retries, a scan spent 35 minutes on 8 images and scanned none. Alibaba Cloud's `ListInstanceEndpoint` gives each endpoint's `Enable`, `AclEnable` and `AclEntries`; only whether there is an allowlist is kept, never its entries, and without internet access the VPC host is pulled from.
- **Results in an older shape stay readable** (`upgradeScan`, `READABLE_FORMATS`): bumping `IMAGE_FORMAT` makes every image be pulled and read again, and until it is, its last result is still shown, with what it lacks as unknown.
- **Trivy is in the Docker image** (from 2026-11-23, about 210 MB), with the other scanners. Like Syft, Grype and Amass, a missing Trivy (run from a clone, or `KEELSON_TRIVY=off`) is a coverage gap (`trivy`), only when there is something to scan.

### Compliance

- **Frameworks are indicative checklists over the checks Keelson already runs**, never checks of their own and never an assessment: ISO/IEC 27001:2022 (all 93 Annex A controls) and PCI DSS v4.0.1 (every section, 1.1 to 12.10, of the twelve requirements; the appendices aren't listed). Each is a file in `src/compliance/` registered in `FRAMEWORKS` and `FRAMEWORK_IDS` (`src/shared/compliance.ts`). How to add one: [CONTRIBUTING.md](CONTRIBUTING.md#a-compliance-framework).
- **Checks map to security topics, and controls map to topics** (`src/compliance/topics.ts`), with single checks only where a topic is too broad. A new check needs only its topics and a new framework only its controls, so every platform, today's and later ones, is covered without per-framework work. `test/compliance.test.ts` fails when a check (or Security Center insight class) is in no topic and not in `NO_TOPIC`, when a topic or control names a check that doesn't exist, or when an out-of-scope control has no note saying what it's about.
- **A control's status says only what Keelson can tell from what it reads**, computed on each request from the latest scans and current triage, never stored (`assess()` in `src/compliance/index.ts`): failing (an open finding on a check behind it), passing (every check behind it that applies ran, nothing open), not enough permission (nothing open, but a check behind it was skipped for a coverage gap), undetermined (nothing open, but none of its checks apply to the accounts in view, or one is turned off), and out of scope (no check of Keelson's can speak to it: policies, people, premises). An open finding is a "no" whatever else couldn't run; a "yes" needs every check that applies to have run. A check with nothing to evaluate doesn't hold a control back. Accepted risk and false positives don't fail a control, and the accepted count is shown.
- **No evidence is asked for or recorded.** The maintainer wants an indication, not a compliance platform: there is nothing to fill in, no "not applicable", and no "needs evidence". Where Keelson can't tell, the page says so (not enough permission, or undetermined); where it never could, the requirement is out of scope.
- **Never claim compliance.** The page, export and docs call the statuses an indication from Keelson's checks, not an assessment or a certificate. ISO certification also needs the management system (clauses 4 to 10), which Keelson doesn't look at; Sonar isn't a PCI Approved Scanning Vendor (11.3.2). For PCI DSS, the cardholder data environment is chosen with the view picker; nothing else scopes it.
- **Control numbers and short titles only.** The standards are copyrighted: every note and topic description is in Keelson's own words. A note says what in the control Keelson can't see.
- Next, not built: more frameworks (SOC 2, CIS benchmarks). Checked on 2026-11-17: PCI DSS v4.0.1 is current (the Council took comments on it from June to July 2026, no successor announced), and ISO/IEC 27001:2022's Annex A wasn't changed by Amendment 1 (2024).

### Networks

- **A platform's requests leave through the network chosen for it** (the Networks page, under Manage; what people set up is in [docs/networks.md](docs/networks.md)). A network is a proxy to send through (HTTP, HTTP over TLS or SOCKS5, with an optional sign-in), the certificates to trust when the network inspects TLS, or both. Each platform is set to a network, to the machine's own connection, or to the default; the default also carries what Keelson reads for itself (CISA's catalog, support dates, AWS's address ranges, scanners' databases, update checks, alerts). It is chosen per platform, as the maintainer asked; per account or per entity is not built.
- **Keelson never runs a VPN or zero trust client.** A tunnel changes the routes of the whole machine, so it couldn't be chosen per platform, and it needs privileges (NET_ADMIN, a tun device) and binaries the image doesn't have. Netskope and Zscaler clients already steer the machine's traffic and need only their certificate trusted; Cloudflare WARP has a local proxy mode; Tailscale has userspace proxies; OpenVPN and WireGuard need a client beside Keelson that offers a proxy. `NETWORK_KIND_INFO` (`src/shared/networks.ts`) holds each kind's label, steps and usual address: the kind only picks wording and what the form starts with, every network is sent to the same way, and a new product is one entry there. The steps were checked against Cloudflare's and Tailscale's own docs on 2026-11-20; don't name or link a third party's container image in them.
- **Every outbound request goes through `src/core/net.ts`**: `request()` for a platform's API, `ownRequest()` (or `own()`) for what Keelson reads for itself. A scan, adding an account and the image backlog run inside `through(route, …)` (`AsyncLocalStorage`), so the route reaches every request below without being passed along, and `runChild` gives the scanners it starts the route's proxy and certificates in their environment (`childProxyEnv`; a scanner's own database download is wrapped in `own()`). With no network chosen `request()` is the global `fetch`, which is what the mocks replace. `test/networks.test.ts` fails when a file in `src/` calls `fetch` or opens a connection of its own; the one exception is Amass's engine, asked on this machine's own port.
- **No dependency for it.** The transport is `node:https` with an agent whose connections are tunnels: an HTTP `CONNECT` or a SOCKS5 handshake written over `node:net`, then TLS with the public authorities plus the route's own. A SOCKS5 proxy is given the name, not an address, so names that exist only inside the network resolve there. Connections are kept per route (`Route.key`) and dropped when its network changes (`forgetRoute`). It keeps `fetch`'s behaviour for what the clients use: redirects, a timeout rejecting with the signal's own `TimeoutError`, and `cause.code`.
- **A network's certificate is trusted only on its own route**, never for the whole process (no `NODE_EXTRA_CA_CERTS`, no global dispatcher), so a company's inspection authority can't vouch for another platform's traffic.
- **"This host doesn't exist" is believed only from a resolver that can be believed.** AWS and Alibaba Cloud read a host that doesn't resolve as a service not offered in a region. A proxy only says it couldn't connect, so `nameExists` asks the machine's own resolver, and returns "doesn't exist" (`ENOTFOUND`) only when that resolver also resolves a public name (`example.com`). A resolver that knows nothing outside its own network would otherwise turn every proxy failure into "not offered", and a check on what wasn't read would pass.
- **A scan through a broken network fails at once** (`checkRoute` in `src/networks.ts`): before the scan, one GET to the platform's `checkHost` (or the account's own instance, `originFor`) without a credential, and a `NetworkError` marked `broken` (the proxy is down or refuses the sign-in, a certificate isn't trusted because the network's own is missing) fails the scan with its own message. Without it every request failed three times over and the scan ended minutes later with every source a coverage gap. Any other failure is left to the scan.
- **The proxy's password is in the vault** (`networks.secret_id`), pruned with the accounts' credentials by `pruneVault`, which keeps both. No API response returns it or a certificate's text: a row says whether a password is stored and who each certificate names. Errors are written without it. A pasted private key is refused.
- **Only admins see or change networks** (`networks` permission, instance-wide): proxy hosts are internal names, so even reading needs it, unlike other pages. A user limited to some entities never does.
- **Test** (`POST /api/networks/test`) sends one GET per platform to its `checkHost` (for a self-hosted platform, to each instance a connected account is on: `testTargets`) through the route, and one to Cloudflare's trace page for the address requests come out at; it works on settings not saved yet, and stores nothing. The mock dev server answers both (`dev/mock/networks.ts`), so it never opens a connection.
- Not built: a network per account or entity, DNS through a proxy for Sonar's and Amass's own lookups, and `SSL_CERT_FILE` on macOS (Go reads the keychain there, so a scanner Keelson runs doesn't trust a certificate only Keelson knows).

## Hard rules

These are never broken. A test enforces most of them.

- **The scanner only reads.** REST calls are GET. Cloudflare's GraphQL is POST but query-only. GitHub's installation token request is a POST that creates a token limited to read permissions. AWS services whose APIs only accept POST are sent only the read actions named in `READ_ACTIONS`. Alibaba Cloud's APIs accept GET for writes too, so its client sends only the Describe, List and Get actions its policy names (`src/shared/alibaba.ts`). `test/integration.test.ts` (Cloudflare), `test/vercel.test.ts` (Vercel), `test/aws.test.ts` (AWS), `test/alibaba.test.ts` (Alibaba Cloud), `test/github.test.ts` (GitHub), `test/gitlab.test.ts` (GitLab) and `test/gitea.test.ts` (Gitea; both GET only, to the instance whose address the user entered) fail on anything else. Sonar sends only GETs, to crt.sh, Shodan and public DNS, and nothing to the entity's own hosts; `test/internet.test.ts` fails otherwise. Scanning container images pulls them from the entity's registries, which only reads, with a registry login asked for through a read action (`ecr:GetAuthorizationToken`, `cr:GetAuthorizationToken`). Never add a write call to any provider, even behind a flag. This matters most where a provider can't issue read-only tokens: Vercel tokens can do whatever their user's role allows, so Keelson is what keeps them read-only.
- **Secret values are never read or stored.** Vercel environment variables are listed without `decrypt` and their values dropped; drain and webhook URLs keep only scheme and host; drain headers are dropped. Secrets are judged by name, type and Vercel's own flags. AWS policy documents are dropped as they're read, a load balancer rule's header condition keeps only the header's name, environment variables and start-up scripts are scanned in memory and only the kind of credential found is kept, and a Secrets Manager secret's value is never asked for. GitHub secret scanning alerts are read without the secret's value. A Gitea webhook keeps the scheme and host of its address and never its secret or authorization header, and a push mirror only its host. Alibaba Cloud is held to the same as AWS, and is never asked for an OSS object or a KMS secret's value. A container image's files, environment variable values and labels are never kept: only its packages, their vulnerabilities, the version of a runtime it records in a known variable, the repository and base image it names, and the kind and place of each credential found in it. `test/vercel.test.ts`, `test/aws.test.ts`, `test/alibaba.test.ts`, `test/github.test.ts`, `test/gitlab.test.ts`, `test/gitea.test.ts` and `test/images.test.ts` check the stored data. GitLab CI/CD variables are never asked for: the API returns their values.
- **A check whose data couldn't be read is skipped, never passed or failed.** Missing permissions become coverage gaps (`src/core/sources.ts`), not errors.
- **Secrets never leave the vault.** Credentials of every provider (tokens, access keys) and the passwords of networks' proxies are stored in `<data-dir>/credentials.json` (mode 0600), and the database holds only a token ID. No API response, log line, test fixture or screenshot may contain a token, a real account ID, a hostname or an email from scanned data (a Keelson username may be an email address the admin chose; only admins can list users). `test/server.test.ts` checks the API responses, and `test/networks.test.ts` a network's password and certificates.
- **Entities stay apart.** Alerts go to each entity's own Slack channel or webhook. Owner suggestions come only from the same entity. An entity left out of All accounts stays out of combined views and exports, including a hand-picked set of accounts: `resolveScope` refuses a set that would combine it with another entity. Anything new that aggregates across accounts must respect this, and the entities the user may see (`Repo.view`).
- **`src/shared` is portable**: no `node:` imports and no DOM. The server returns shared DTOs with `satisfies`, and the web imports them as types.
- **Routes carry their guards** (`src/server/router.ts`): `routes(app).with(requireSession(auth))`. Who can reach a route never depends on where it is registered.
- **Every change names the permission it needs.** A route that isn't GET carries `requirePermission(…)` (or `anyone`, only for signing in, signing out, creating the first admin and a user's own password), and `routes()` throws at startup when one doesn't. Roles are checked on the server; hiding a control in the web is only a convenience. `test/users.test.ts` tries every permission as every role.
- **Passwords are only ever stored as scrypt hashes** (`src/server/passwords.ts`), in the `users` table, and no API response or log line contains a hash or a password. One-time passwords are shown once, to the admin who made them (or printed by `--reset-password` for the operator), and never stored.
- **Migrations are append-only.** New ones go at the end of `MIGRATIONS` in `src/store/db.ts`, ship only in a new release line, and their fingerprint goes in `test/migrations.test.ts`. Never edit a shipped migration.
- **Don't quote a total check count** in the README, the docs, images or the changelog. It goes stale with every new check.

## Node.js, the image and tooling

- **Keelson ships only as a Docker image** on GHCR, for `linux/amd64` and `linux/arm64`. Nothing is published to npm: package.json is `private`, and `test/env.test.ts` fails if the release workflow publishes to npm. Docs and the in-app upgrade steps describe the image and its release-line tag; running from a clone (`npm start`) is for development and gets `git checkout` steps.
- **The image stays small.** Its final stage is Alpine with only the Node.js binary copied from `node:26-alpine` and the libraries Node's own Alpine image installs for it (libatomic and libstdc++; the build runs `node --version` to catch a missing one): no npm, Yarn or Corepack, which also keeps their dependencies out of image scans. Keep the two Alpine versions in the Dockerfile equal. The build stage runs on the build machine's platform, so runtime dependencies must be plain JavaScript (tested). Every scanner Keelson runs (Syft, Grype and Grant, about 85 MB each, Trivy about 210 MB and Amass about 55 MB) is the exception the maintainer chose: release archives pinned by version and SHA-256 sum per platform, and `inImage` in `src/shared/tools.ts` says which are there (a test ties the two). CI fails when the image passes 800 MB, contains npm, can't run the scanners, or doesn't run as uid 1000 (the uid earlier images used, so `/data` volumes stay readable). Weigh any new runtime dependency or OS package against that.
- **Node.js 26 LTS only.** The minimum is 26.13.0, the first Node 26 LTS release. `NODE_MAJOR` and `MIN_NODE` in `src/node-check.ts` are the source of truth, and `engines` in package.json says the same (tested). `.nvmrc` says `26`, the image runs `node:26-alpine`'s binary, and CI tests on 26. `src/bin.ts` runs `checkNode` before importing anything else, so a clone run on an older Node.js prints the upgrade command for the user's Node manager (nvm, fnm, Volta, Homebrew, winget). `src/node-check.ts` imports nothing, so it runs on old Node.js; don't add imports to it.
- Biome 2.6 is used for both lint and format (`biome.json`: 2 spaces, 160 columns, double quotes, trailing commas). TypeScript runs with type stripping, so use `.ts` extensions in imports and no enums or namespaces.
- Dependabot ignores major updates of `@types/node` and the Docker `node` images (`.github/dependabot.yml`). Those move together with `NODE_MAJOR`, by hand.
- GitHub Actions use current majors (checkout and setup-node v7, CodeQL v4, Docker actions v4–v7).
- **`.claude/settings.json` is shared** with everyone who uses Claude Code here. It lets the checks, tests, formatting, docs, build and the mock dev server run without a prompt, and denies `npm run release`, `npm run sync` and reading `.keelson/` (real scan data and tokens). Keep it to commands that are safe on any clone; personal permissions go in `.claude/settings.local.json`, which git ignores.

## Users and roles

- **Everyone signs in with their own account.** There is no shared password and no sign-in-free local mode: the first person to open Keelson creates the admin (`/api/setup`), and the admin adds everyone else on the Users page. Off loopback, creating the admin needs the setup code printed at startup, so whoever finds a new instance first can't take it. `KEELSON_AUTH=none` turns sign-in off for an authenticating proxy, and then everyone is an admin.
- **Four roles, each including the one before** (`ROLES`, `PERMISSION_ROLE` and `ROLE_INFO` in `src/shared/roles.ts`): Viewer reads everything and exports; Analyst also triages and runs scans; Manager also connects accounts, edits entities and alerts, and tunes checks; Admin also manages users, Settings and Networks. Every role sees every page. A new kind of change gets a permission in that table, starting at the lowest role it is safe for, and the role summaries, the README's table and `Terms`-style copy say what it allows.
- **An admin can limit a user to some entities** (`user_entities`; null means every entity, admins are never limited). Everything such a user reads or changes goes through `Repo.view` and `src/server/access.ts`, so another entity's accounts, findings and scope keys answer 404, as if they didn't exist. "All accounts" is their entities, still without those kept out of it. A limited user can't make the changes that reach every entity (`INSTANCE_WIDE` in `src/shared/roles.ts`: checks, settings, networks, users), and can't create, remove or arrange entities (show in All accounts, order); a limited manager adds accounts to and edits only their own entities. Any new route that lists or changes accounts, entities or findings must use those helpers; `test/users.test.ts` tries every route as a limited user.
- **New people get one-time passwords**, made by Keelson and shown once to the admin, and must replace them before anything else (`mustChangePassword`). There is no email; Keelson sends nothing to people. Resetting a password and removing a user sign that person out everywhere at once. Keelson always keeps one admin, and an admin can't remove themself. `--reset-password <username>` is the way back in for a locked-out admin.
- **Triage records the username** of whoever changed it.

## Code conventions

- **Settings are `KEELSON_*` variables**, read with `env()` from `src/env.ts`, never `process.env.KEELSON_…` directly. The Docker image sets only `KEELSON_INSTALL=docker`; its defaults (`0.0.0.0`, `/data`) live in `src/env.ts`.
- **Every file starts with a short comment saying what it is and why.** Comments explain *why*, not what the code does.
- **Server:** Hono, with one route module per area in `src/server/routes/`. Request bodies are validated in `src/server/validate.ts` before any write. Scoped routes read `c.get("scope")` (`all`, `e:<id>` or `a:<id>`, resolved in `src/shared/scope.ts`).
- **Store:** SQLite, with one repository per concern behind `Repo` (`src/store/repo.ts`). Triage belongs to the finding's fingerprint (check, account, zone, resource), not to a scan, so it survives rescans. Every triage change is recorded in `triage_events`.
- **Checks:** follow [CONTRIBUTING.md](CONTRIBUTING.md#adding-a-check). Report passes as well as failures. Use `confidence: "likely"` for heuristics and `"confirmed"` for probes. Each new check gets a failing case in `test/checks/cases.ts`. Aim for checks that go deeper than other tools, for example correlations across sources and GraphQL traffic evidence, while keeping the finding text plain.
- **Tests:** every bug fix or feature comes with a test that would have caught it. Server behaviour is tested through the app (`test/helpers/app.ts`, `makeApp`) against the mock Cloudflare (`dev/mock/cloudflare.ts`), mock Vercel (`dev/mock/vercel.ts`), mock AWS (`dev/mock/aws.ts`) and mock GitHub (`dev/mock/github.ts`, whose App key is made when it loads, so JWTs are really checked) mock GitLab (`dev/mock/gitlab.ts`) and mock Gitea (`dev/mock/gitea.ts`). Each Vercel check has a failing case in `test/vercel-cases.ts`, each AWS check in `test/aws-cases.ts`, each GitHub check in `test/github-cases.ts`, each GitLab check in `test/gitlab-cases.ts`, each Gitea check in `test/gitea-cases.ts`, and each Sonar check in `test/internet-cases.ts`, against the mock crt.sh, Shodan and DNS in `dev/mock/internet.ts`. The mock data must stay fictional.
- **AWS API shapes** come from the AWS API references (`https://docs.aws.amazon.com/`). As with Vercel, a missing field is unreadable or not configured, never a pass.
- **GitHub API shapes** come from GitHub's REST reference (`https://docs.github.com/rest`), with the API version pinned in a header (`X-GitHub-Api-Version`). A missing field is unreadable or not configured, never a pass: an organization without its security settings in the answer means the App lacks Administration, and is a coverage gap.
- **Vercel API shapes** come from Vercel's OpenAPI description (`https://openapi.vercel.sh/`). Check field names there before reading a new one, and treat a missing field as unreadable or not configured, never as a pass.

## Web UI conventions

The UI follows **Cloudflare's design language** using Kumo (`@cloudflare/kumo`), with Phosphor icons and Tailwind. The maintainer asked for no "AI slop" design: no gradients, emoji, decorative cards or made-up components where Kumo has one.

- **Use the shared building blocks** in `web/src/components/ui.tsx`: `Page`, `Card`, `ListCard`, `SettingRow` and `SettingRows`, `FormGrid`, `DialogHeader`, `PageState`, and the badges. Use the shell state from `web/src/shell.tsx` (`useShell`, `useScopedApi`). Every page is listed in `web/src/routes.tsx`.
- **Alignment is strict.** Fields that share a row line up their labels and controls on one baseline, and descriptions sit below the control (`FormGrid`). Spacing comes from the shared components, not from one-off margins. Lines that meet across panes meet exactly (the sidebar header and the top bar are both `h-14`, border included), text in a card's toolbar, rows and footer starts on one edge, and table headings never wrap (`web/src/styles.css`). An icon beside a title that can wrap sits in the text flow (`inline-flex align-middle`), not in a wrapping flex row, so it never ends up on a line of its own.
- **On phones the top bar keeps the entity's name:** the platform picker and Run scan show only their icons below the `sm` breakpoint.
- **Hierarchy:** an entity name always reads as the parent of its account names (entity, then account). Where accounts from several providers mix, an account name carries its provider glyph (`AccountName`, `ProviderIcon`).
- **Provider-specific pages** declare `providers` in `web/src/routes.tsx` (Zones for Cloudflare, Projects for Vercel, Regions for AWS, Resources for Alibaba Cloud, Repositories and Dependencies for GitHub, GitLab and Gitea, Images for AWS, Alibaba Cloud, GitHub and GitLab) and are hidden when no account in view is on that provider. Sonar's Attack surface page is the exception: it always shows, and offers to set Sonar up where it isn't watching. Wording says the provider's own words (`PROVIDER_INFO`: "team" for Vercel, "access key" for AWS's credential, "AccessKey" for Alibaba Cloud's, "console" for their dashboards, "organization" and "GitHub App" for GitHub, "group" and "project" for GitLab, "organization" and "access token" for Gitea) and never assumes a provider.
- **After sign-up the app opens on the Overview**, with or without accounts. With nothing connected (`useShell().empty`), the Overview shows `GetStarted` (`web/src/pages/Setup.tsx`), whose Add accounts opens the Add accounts flow (`/accounts/add`); other pages that need an account say so in a line, and pages for one platform stay out of the sidebar. Adding accounts ends on a summary whose first action is the Overview. There is no separate setup page.
- **Adding accounts is a flow of its own, not a dialog** (`web/src/pages/AddAccounts.tsx`). `/accounts/add` is the platform catalog: a card per platform, grouped by `PROVIDER_INFO.category` (`PLATFORM_CATEGORIES`), searchable by its name, services and `keywords` (`matchesProvider`), with how many of its accounts are connected. It must work for dozens of platforms, so no list of radio buttons and nothing laid out by hand: a new provider only needs its `category` and `keywords`, and a new category only when none fits. `/accounts/add/<platform>` shows that platform's `TokenHelp` beside the steps (credential, accounts, entity, what it can read; state in `useConnect`, parts in `web/src/components/connect.tsx`), and ends on a summary with what to do next. `?entity=<id>` carries the entity it was opened from (an entity card's Add accounts and Watch from the internet). The credential is held in memory only, never in the address; a reload starts again from it. Someone on one platform never reads another's steps. The credential's inputs come from `PROVIDER_INFO.fields` (`CredentialFields`): one for a token, two for an access key. Old `/accounts?add=1` links are sent to the flow.
- **Multi-step flows show where you are** with `Steps` (`web/src/components/ui.tsx`), a line of its own on phones.
- **One vocabulary** in everything a user reads: **platform** (Cloudflare, Vercel, AWS, Alibaba Cloud, GitHub, GitLab, Gitea; the code says `provider`), **entity** (who owns accounts), **account**, **location** (a zone, project, region or repository: `zoneWord` gives the platform's own word, or "Location" when the view mixes platforms), **check** (a rule), **finding** (one resource failing a check) and **control** (one requirement of a compliance framework, which Keelson's checks can indicate). `Terms` in `web/src/components/ui.tsx` explains them on the Accounts page; keep it in step with any new term.
- **The nautical theme names modules, never everyday terms.** Keelson's own modules and brand may carry a ship or navy name (for example Sonar for discovery from outside, Boarding party for the AI pentester, Ship's log for cloud activity, Manifest for inventory, Drydock for checks before code ships). Each such name always appears with a plain description beside it ("Sonar: external attack surface"). The vocabulary above, and anything in a finding, alert, export or report, stays plain. Small touches (the logo, empty states, the scan schedule as a "watch", release names) are fine where they don't replace a plain term.
- **A finding says where it is in the entity.** The finding view's "In your infrastructure" (`web/src/components/located.tsx`) follows every public address and known hostname a finding names into the entity's other accounts (`src/server/locate.ts`): found (with what holds it and a console link), released, not in the entity's accounts (only when every cloud account lists its addresses), or nothing to say. A finding about a port is checked against the holder's open inbound rules or listeners. It reads `ProviderLinks` and the resource view only, so a new provider joins by publishing its addresses (`…Addresses`, `…Exposure`), load balancers and DNS records and adding their keys to the lists at the top of `locate.ts`. Never across entities.
- **A finding says where it is from.** `PlatformMark` shows a finding's, check's or group's platform icon wherever platforms mix, and both sides joined by arrows for a check that compares platforms (`spans` on the check, carried on `Finding`, `FindingBrief`, `FindingGroup` and `CheckRow`). Every `XP-` check declares `spans`; a test fails if one doesn't. Use it in any new list of findings.
- **The sidebar has four sections** (`NAV_GROUPS` in `web/src/routes.tsx`): Posture (every platform), Inventory (one page per platform), Insights (what a platform reports besides configuration) and Manage (Keelson itself). A page limited to some platforms shows their icons next to its name.
- **Filters are grouped by what they narrow**: what the finding is (category, confidence, who reported it, correlation) and where it is (location), with severity, account and the platform switch outside the menu. A chip names what it filters ("Category: DNS").
- **Links are Kumo's `Link`.** An in-app `href` routes through the app and keeps the scope (`AppLink` in `web/src/components/ui.tsx`, given to Kumo's `LinkProvider` in `App.tsx`); an action that reads as a link is `<Link render={<button …/>}>`. A copyable value is `ClipboardText`, an icon-only control is a `Button` with `shape="square"`, and a screen with nothing to show is `Empty` in a `LayerCard`. `test/web-design.test.ts` fails on an anchor or button styled with `text-kumo-link`.
- **Kumo specifics:** a `DropdownMenu.Label` must sit inside a `DropdownMenu.Group`; outside one, opening the menu throws and blanks the page. give `Tooltip` the button through `render={<Button …/>}`. Wrapping a button in a tooltip trigger nests one button in another. Use `ButtonGroup` for split buttons, and `Autocomplete` for free text with suggestions.
- **Finding dialogs** are at least 75% of the screen width on desktop (`sm:w-[75vw]`). J and K move through the list, and only when focus isn't in a field.
- **Type less, pick more.** When a field asks for a value the app already knows, offer it. Owners suggest the owners already used in the entity (`GET /api/owners`). A new entity name that matches an existing one is caught, and the add-accounts form offers to use the existing entity. The Link URL offers the current address. Apply this to any new field.
- **A control a role can't use is hidden, or shown read-only** (`useShell().can(permission)`), and a page a role can't open declares `permission` in `web/src/routes.tsx`. Don't show a button that only answers "your role can't".
- **Actions do what their label says for the current view.** "Run scan" scans the selected account, or the entity or All accounts when that is the view, and its menu offers the wider scopes. Tooltips say what will happen.
- **Lists let people pick rows and take them elsewhere** (`web/src/components/selection.tsx`): a checkbox per row (`SelectRow`) and for the page (`SelectPage`), and while anything is picked the toolbar becomes `SelectionBar`, which offers "Select all N that match" once the page is ticked, the list's actions, and Clear selection. The actions are a `CopyMenu` (one value per line, deduplicated, with a toast saying how many) and a CSV download. A selection starts over when the filters change. Lists the server pages (Dependencies) ask the server for what a selection covers (`/api/sbom/affected`, at most 200 picked keys in the address, or none for every row that matches); lists the browser holds do it themselves. Copy through `copyText`, never `navigator.clipboard`, which browsers withhold on a team server over plain HTTP (`test/web-design.test.ts`). Lists without row checkboxes offer "Copy shown" for what the filters show. A new list of things people act on outside Keelson (repositories, hosts, addresses, packages) gets this.
- **A row that names the first few of a group opens the rest.** Where a row groups many things (the images a vulnerability or a component is in, the versions a vulnerability affects, the workloads that run an image, the repositories that use a package, a workload's hostnames), it shows the first few and a count, and the count is a link (`MoreLink`, or `MoreNames` for a plain list of names, in `web/src/components/full-list.tsx`) that opens every one of them in a dialog, on the same page: a filter, Copy with one entry per column that is worth copying (one value per line, without repeats), and a CSV that carries every column, the ones the table leaves out included (`csvOnly`). A list is described once by its columns (`FullListColumn`; the text rules are `src/shared/lists.ts`), and the same columns serve wherever that kind of row appears: `IMAGE_COLUMNS` and `WORKLOAD_COLUMNS` in `web/src/components/images.tsx` are also what the Images tab's selection copies and exports. There is one dialog for the app (`FullListProvider` in `App.tsx`), opened with `useFullList()`, so a link in each of fifty rows costs nothing until it is clicked. When the rows aren't in the browser, the list asks the server under the page's own filters, so it is the list the row counted (`GET /api/images/within` for the images a vulnerability or component is in). Never write "and N more" as plain text: `test/web-design.test.ts` fails on it.
- **A page must stay light on any laptop.** A list that grows with the size of an account (images, packages, vulnerabilities, findings across accounts) is filtered and paged on the server, 50 rows at a time; a row carries a count and the first few of a longer list, not all of it; a list searched on the server takes its search from `SearchBox` (`web/src/components/search.tsx`), which waits for a pause in typing before it asks, never rewrites what is being typed, and shows a spinner until the rows on screen are the ones for what it says; the list keeps its rows, dimmed, until the next ones arrive (`keep` on `useScopedApi`, `shownFor` in `src/shared/fetched.ts`) and draws them at low priority (`useDeferredValue`), so a key is never held up by the table; and a hint on every row of a table is a `title`, not a Kumo `Tooltip`, which mounts a component per row. The shell refreshes the scan status every two seconds while a scan runs (every ten while images are read in the background), and every page that reads it is drawn again: a table of hundreds of rows turns that into a constant load. A table of rows is wrapped in `memo` and given props that stay the same objects (`useSelection` returns one until the selection changes), so that refresh doesn't draw its rows again: on the Images page fifty rows cost about 90 ms every second of a scan until they were. The server keeps what it builds from scans until a scan changes, and never holds every result of an account in memory to answer one page.
- **Bulk edits change only the fields the user touched.** Clearing a field is a separate, explicit choice, and every bulk change can be undone.
- `localStorage` is for per-browser conveniences only (theme, last scope), and every read is wrapped in `try`.

## Writing

The same rules apply to UI copy, docs, changelog and commit messages:

- **Describe Keelson by where it is going, and never claim what isn't built.** The one-line description is "One place for the security of your whole infrastructure", with what it does today said in general terms ("checks your cloud, edge and hosting platforms") and anything planned marked as next. Descriptions never name platforms; the README body and docs list them. It is used in the README, the GitHub description, the image label, package.json and the social card (`docs/images/social-preview.html`).
- **Plain, specific English** for someone running Keelson, not a reviewer. Say what happens and what to do. Write sentences, and avoid jargon and marketing.
- **UI copy** names the thing the user sees. Error messages say what's wrong and the fix ("Mock Group already exists. Pick another name.").
- **Commit messages:** one imperative line that says what changed for the user (for example "Run scan scans the selected account, with a menu for the entity or every account"). No AI attribution or co-author trailers.

## Changelog, versions and releases

- **Every user-visible change adds a line under `## Unreleased` in `CHANGELOG.md`**, in the same commit. Mark it `**Breaking:**` with the steps to take if users must act. The release script refuses a breaking change or a new migration within the same release line.
- **Releases are cut locally with `npm run release -- <patch|minor|major|rc>`** (`--dry-run` to preview). It requires a clean `main`, syncs with `origin/main`, runs `npm run check`, bumps, commits `Release vX.Y.Z`, tags, and pushes `main` and the tag in one atomic push. Before 1.0, breaking changes and migrations are `minor`. The tag starts `.github/workflows/release.yml`, which only publishes: the image to GHCR (`:X.Y.Z`, `:X.Y`, `:latest`; candidates only `:X.Y.Z-rc.N`) and GitHub Releases. Running installations read the release to show updates and breaking-change warnings.
- **The workflow never commits or pushes to `main`** (`test/release.test.ts` enforces it), and there is no "Run workflow" button. When CI made the release commit, every release forked `main` from the maintainer's clone. Don't bring that back.
- **Catch up with `npm run sync`** rather than `git pull`: it merges `origin/main` and moves notes that a merge landed under a released version back to `## Unreleased` (`repairReleasedNotes`), committing the repair. The tests fail while released notes differ from their tag, and point at `npm run sync`.
- Agents never run `npm run release` or `npm run sync`'s merge on their own: releasing is the maintainer's call, and both commit (and `release` pushes).
- The README and `docs/deployment.md` pin the current release line (`ghcr.io/r4reetik/keelson:0.6`). `scripts/release.ts` (`pinLine`) updates them on each new line, so don't edit those pins by hand.
- Releases come only from `main`. Older lines get no backports.

## How to work here

These apply in every session, whoever you're working with:

- **Design for more providers.** Google Cloud, Google Workspace and others are planned, so UI and code choices should work for any number of providers, not the seven there are now.
- **Treat every real account as production.** Use the mock (`npm run dev -- --mock`) by default. Against real accounts, run nothing that writes, never print a token or a private key, and delete any scratch copies of `~/.keelson` you make. A Cloudflare token for Keelson is read-only, an AWS access key should belong to a user with only the SecurityAudit policy (and the three ECR read actions for pulling images, when images are scanned), an Alibaba Cloud AccessKey to a RAM user with only Keelson's policy (`alibabaPolicy()`), and a GitHub App should have read-only permissions, a GitLab token the read_api scope only, and a Gitea token read scopes only; a Vercel token can't be read-only, so Keelson's GET-only rule is what protects it.
- **A dev server left running in this clone follows your edits.** `npm run dev` restarts on every change to `src/`, so a migration you add is applied to the real `./.keelson` database the moment you save it (after a backup in `.keelson/backups/`), and code that isn't finished runs against real accounts. Say so when it happens. To look at your work, run the mock on other ports (see Commands) instead of opening the copy on the default ports, which may hold real data.
- **Accept Vercel tokens quietly**: no warning when the token's user can write (see the decision log).
- Confirm before anything destructive or outward-facing.
- When asked for "everywhere", apply the change across the whole app and its docs, not only the place that was named.
- Verify UI changes in a browser against the mock, not just with tests, and say what wasn't checked.
- No attribution lines (`Co-Authored-By`, "Generated with…") in commits or pull requests.

### Who you're working with

The maintainer, r4reetik on GitHub, works in a clone whose `origin` is `github.com/r4reetik/keelson` and cuts the releases. Everyone else is a contributor, working on a fork, so their `origin` is the fork. When it isn't clear which you're working with, ask once before committing, pushing or recording a preference.

## Working with a contributor

Most people who clone this repository are contributors. In their sessions:

- **Work on a branch of their fork**, never on `main`. Commit and push to the fork when they ask, and open the pull request against `main` of `r4reetik/keelson`. Never push to `r4reetik/keelson` itself.
- **Catch up with the upstream repository** (`git remote add upstream https://github.com/r4reetik/keelson.git`, then `git fetch upstream` and rebase the branch on `upstream/main`). `npm run sync` and `npm run release` are for the maintainer's clone; they merge into and push `main`.
- **Check before you commit.** `npm run check` must pass, every change comes with a test, and anything a user would notice gets a line under `## Unreleased` in `CHANGELOG.md` (see [CONTRIBUTING.md](CONTRIBUTING.md#pull-requests)).
- **Bigger changes start with an issue**, so the approach is agreed before the code is written: a new provider, a new dependency, a change to a hard rule or to the UI's structure.
- **Decisions are proposed, not made.** If the change makes or reverses a decision, update this file and add a decision-log line in the same pull request, and say so in the pull request description. The maintainer accepts the decision by merging it.
- **The contributor's own preferences stay out of this file.** They belong in their personal agent settings (for Claude Code, a CLAUDE.local.md file, which git ignores, or its memory), not in the project's rules.
