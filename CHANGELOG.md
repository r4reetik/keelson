# Changelog

## Unreleased

- **The Docker image includes Trivy and Amass too**, so every scanner Keelson runs comes with it: container images in your registries are scanned, and Sonar runs OWASP Amass on the entity's domains, without installing anything. Pull the new image and scan again. Trivy downloads its vulnerability database (about 1.6 GB) into the data folder on the first scan with images to read. The image is larger for it, about 265 MB more.
- **The Dependencies page says what a missing scanner needs, too.** When a view has no SBOM because Syft, Grype or Grant couldn't run, the page said the scanner wasn't in the Docker image and told you to replace the credential; it now says the same as Data coverage: in the Docker image, that the image includes it, and from a clone, to install it on that machine. Other pages that show nothing for a source they couldn't read name the platform's own credential instead of "the credential".

## 0.18.1

- **The Docker image includes Anchore's Syft, Grype and Grant.** GitHub, GitLab and Gitea repositories get their software bill of materials, vulnerable and malicious packages and license findings without installing anything: pull the new image and scan again. Grype still downloads its vulnerability database (about 3 GB) into the data folder on the first scan. The image is larger for it, about 255 MB more.
- **Data coverage says what a missing scanner needs where Keelson runs.** A source that comes from Syft, Grype, Grant, Trivy or Amass no longer says the platform reported it, or tells you to replace the platform's credential. In the Docker image it says whether the image includes the scanner; run from a clone, it says to install it on that machine and links to its install steps. The Overview's banner no longer blames the account's credential for a scanner that isn't installed, and a credential row names the platform's own credential (access key, GitHub App…) instead of "token".

## 0.18.0

- **Share a Keelson run from a clone with your local network.** Started on every interface (`--host 0.0.0.0` or `KEELSON_HOST=0.0.0.0`), Keelson now prints the addresses other machines on the network open, under **Network**, instead of only `localhost`. In development, `npm run dev -- --host` does the same for the API and the page with hot reload (add `--mock` for mock data, or an address after `--host` to share on that one only). The default is still this machine only. It is plain HTTP: use it on a network you trust, or put a proxy with TLS in front.
- **GitLab is the seventh platform, on gitlab.com or your own instance.** Add a top-level group with the address you open GitLab at and an access token that has only the `read_api` scope (a group access token with the Owner role fits best); Keelson sends nothing but GET requests to that address's `/api/v4`. It checks whether the group requires two-factor authentication, how many owners it has, and whether projects can be shared with outside groups; default branches that developers can push to without a merge request, that take force pushes, where an approval survives new commits or the author can approve, and where maintainers push past merge requests; webhooks over plain HTTP or without certificate verification; deploy keys that can push, and deploy tokens that can write and never expire. Projects in subgroups are included, and all of them are on the **Repositories** page. CI/CD variables are never read, because GitLab's API returns their values. GitLab tokens expire: the Accounts page shows the date.
- **GitLab dependencies, CI includes and images.** With Syft, Grype and Grant installed, each project gets a software bill of materials from its manifest and lock files (never the code), on the **Dependencies** page with GitHub's and Gitea's, and the same findings: exploited, vulnerable and malicious packages, missing lock files and strong copyleft licenses. Where GitHub's check is on third-party actions, GitLab's is on what a pipeline **includes** from outside the group: another project's file by a branch or tag, a CI/CD component at a moving version, or a file at a web address, all of which run with the project's CI/CD variables. Container registry images are listed on the **Images** page with the project that builds them and where they run; images in public projects are scanned with Trivy, and ones in private or internal projects are listed only, because GitLab's registry would need the access token itself.
- **GitLab joins the checks that span platforms.** A DNS record on Cloudflare, Route 53 or Alibaba Cloud DNS that points at GitLab Pages when no Pages site in the entity's groups uses that hostname (XP-028, XP-034, XP-033). On AWS and Alibaba Cloud, a role that GitLab CI in any project can assume (AID-016, LID-016), one that trusts GitLab groups outside the entity (XP-029, XP-031), and one that anyone who can push to a project can assume, because its trust allows any branch or a default branch developers push to directly (XP-030, XP-032). These work for gitlab.com and for your own instance, once one of its groups is connected. Sonar and a finding's "In your infrastructure" know GitLab Pages domains too.
- **Gitea is the sixth platform, for the repositories you host yourself.** Add an organization with the address you open your Gitea at and an access token that has read scopes only (organization, repository and user); Keelson sends nothing but GET requests to that address's `/api/v1`, and never follows a redirect. It checks members who sign in without two-factor authentication (rated higher for owners; this needs a site administrator's token with the admin read scope, and is skipped without it), how many people own the organization, teams other than the owners that administer every repository, people outside the organization who can push to or administer a repository, deploy keys that can push, default branches that take pushes without a pull request, rules that allow force pushes, let an approval survive new commits or let administrators merge past them, webhooks that deliver over plain HTTP, private repositories a push mirror sends to another server, and public repositories the instance hands to anyone without a sign-in, which Keelson confirms with one request that carries no token. Its repositories are on the **Repositories** page beside GitHub's. A webhook keeps only the scheme and host of its address, never its secret or authorization header, and a push mirror only the host it pushes to. Forgejo serves the same API. Container packages and Gitea Actions' own settings aren't read yet.
- **Dependencies of Gitea repositories.** With Syft, Grype and Grant installed where Keelson runs, a Gitea scan keeps a software bill of materials for each repository, as a GitHub scan does: it lists the default branch's files, fetches only manifest and lock files, workflows (from `.gitea/workflows` and `.github/workflows`) and Dockerfiles, never the code, and makes an SBOM again only when one of them changes. Findings are the same six as GitHub's, under Gitea's IDs (`TED-001` to `TED-006`): a dependency attackers are exploiting, one with a critical or high vulnerability, a known malicious package, workflows that run third-party actions by a tag, a project without a lock file, and a strong copyleft license. Gitea repositories and their packages are on the **Dependencies** page with GitHub's, and each has its own page with its projects, packages and SBOM download. A repository the instance mirrors from elsewhere isn't read.
- **A Gitea that only answers inside your network works through Networks.** Choose a network for Gitea on the Networks page: a proxy into the office network or VPN, and your own authority's certificate when the instance uses one. A network's **Test** now also asks each Gitea instance a connected organization is on.
- **Scan a platform through your VPN or zero trust network.** A new **Networks** page (under Manage, for admins) holds the ways Keelson's requests can leave: a proxy into Netskope, Cloudflare WARP, Zscaler, an OpenVPN or WireGuard tunnel, Tailscale or anything else that offers an HTTP or SOCKS5 proxy, and the root certificate to trust when the network inspects TLS. Each platform is then set to a network, to this machine's own connection, or to the default, so a GitHub organization with an IP allow list, an AWS account tied to a source address or a registry with an access list is scanned from an address it accepts while everything else goes out as before. A platform's network carries its scans, adding its accounts and pulling its container images; the default also carries what Keelson reads for itself (vulnerability catalogs, scanners' databases, update checks, alerts). The form shows how to give Keelson a route into each kind of network and fills in its usual address. Keelson doesn't run a VPN client itself: a tunnel would carry every platform's requests, and needs privileges the image doesn't have. See [docs/networks.md](docs/networks.md).
- **Test a network before you rely on it.** **Test** sends one request to each platform through a network, without a credential, and shows which answered, how fast, and the address requests come out at, which is the one to add to a platform's allow list. It works on settings you haven't saved yet. Before every scan through a network Keelson asks the platform one thing the same way: when the proxy is down, refuses the sign-in, or a certificate isn't trusted because the network's own is missing, the scan stops at once and says so in plain words, instead of finishing with every source unread.
- **A network's secrets stay put.** A proxy's password is kept with your platform credentials, outside the database, and no page, API answer, log line or error shows it. A network's certificate is trusted only for requests through that network, never for the rest of Keelson, and a private key pasted by mistake is refused. Only admins see or change networks.

## 0.17.0

- **"and 43 more" now opens all of them.** Where a row shows the first few of a group, the count is a link that lists every one in place: the images a vulnerability or a component is in (with where each runs and which repository builds it), the versions a vulnerability affects, the workloads that run an image, an image's findings and tags, the repositories that use a package, a workload's hostnames, and the shorter lists on Attack surface, Repositories and Scans. Each list has a filter, **Copy** for any one column as lines to paste (images, repositories, hostnames, upgrades to make…), and **Download CSV** with more than the table shows. Picking images on the Images tab copies and exports the same columns.
- **Searching the Images and Dependencies pages no longer feels stuck.** The search box keeps up with typing and never loses a key, asks once you pause (or press Enter), drops the search for what you typed before as soon as the next one starts, and shows a spinner while it searches; the rows on screen stay, dimmed, until the new ones arrive instead of the table emptying each time, and Escape or the × clears the box. On the server a search of components takes a few milliseconds whatever the size of the registry, a search of vulnerabilities no longer goes through every image again, and the server keeps answering other requests while it works on a long list.
- **Alibaba Cloud images behind an allowlist now say why they aren't scanned, instead of using up the scan.** A Container Registry instance whose internet access admits only an allowlist (or that has no internet access) drops connections from anywhere else, so every pull timed out after minutes of retries, a scan spent its time on a handful of images and none was scanned. Keelson now tries such a registry once per scan, marks its images with the reason and shows a coverage gap, "Connecting to Container Registry from where Keelson runs", that says what to change: add the address Keelson connects from to the instance's allowlist (Container Registry console, the instance's **Access Control**, **Internet**), or run Keelson in a VPC linked to the instance. The same applies to an ECR or other registry host Keelson can't reach. Elastic Container Instance in a region that doesn't offer it is no longer a coverage gap, so the container groups that run your images are read again.
- **A scan always reads each repository's latest image, and the rest are read in the background.** The images your workloads run and the newest image of every repository are read by the scan itself, however long that takes; before, a scan stopped after 30 minutes of images and left the rest for the next day's scan. A repository's older builds still get what is left of those 30 minutes, and the ones a scan doesn't reach are now read in the background as soon as no scan is running or queued. The top bar shows its progress ("Reading the remaining images in the background (12/80)"), the Images page says how many are being read, and when an account's images are done Keelson scans the account once more, without pulling anything, so their findings and alerts appear (listed on the Scans page as "Images read in the background"). A scan you start always goes first; the background carries on after it. The first scan of a registry with many repositories takes longer than before: about half a minute for each image never read. If Keelson restarts, unread images wait for the account's next scan.
- **Image scans are much faster after the first: an image is pulled once.** An image named by its digest never changes, so Keelson keeps Trivy's list of what is in it and, on every later scan, matches that list against Trivy's current vulnerability database instead of pulling the image again. A vulnerability published after an image was read still shows up at the next scan, in a fraction of a second per image and without contacting the registry. Only new images are pulled, plus images your workloads name by a tag alone, which are asked for again once a day because the tag may have moved. Images scanned before this are read once more to make their list. An image's page says when it was read and which database its vulnerabilities are from, and the Images page says how many images the last scan pulled and how many it only checked.
- **An inventory of what your images are made of, and an SBOM for each.** The Images page has a **Components** tab: every package, runtime and operating system across the scanned images, at each version, with how many images hold it, whether it has a known vulnerability, the version that fixes it, and whether it is past its end of life. Filter by kind, package type, vulnerable, unsupported, or only what is in internet-facing or running images, and export it as CSV. Each image's page downloads its software bill of materials as CycloneDX (with vulnerabilities) or SPDX.
- **What the base image brought, and runtimes no scanner matches.** Keelson tells an image's base layers from the ones its own build added, so every component and vulnerability says whether it came with the base image (fix: a newer base) or with your build, and an image's page shows what it is built on: the base image it names, the FROM lines of its repository's Dockerfiles, or another of your images whose layers it starts with. The runtime an official image is built around (Node.js, nginx, Python, Go, Java, PHP, Ruby, Redis, PostgreSQL and others) is installed from a tarball and is in no package list; Keelson reads its version from the image and says whether its release line still gets fixes and what its newest release is, from [endoflife.date](https://endoflife.date). An image in use on an end-of-life runtime is now part of the end-of-life finding.
- **The Images page no longer slows the machine down.** Every tab loads 50 rows at a time from the server instead of every image at once, rows carry the first few images and workloads with a count, searching waits for a pause in typing, and the tables are no longer drawn again each time the scan status refreshes. Scanners (Trivy, Syft, Grype, Grant) run at the lowest priority on at most half the machine's cores, with a ceiling on Trivy's memory, and a scan no longer holds every image's packages in memory. A scan now starts with the images it has never scanned, and keeps the newest three images of a repository that were pulled lately rather than every build of the last month, so a large registry is covered in a few scans instead of refreshing the same images. While several accounts are scanned one after another, pages now show each account's results as soon as its scan is done, not when the last one finishes.
- **Images found by a real registry.** An image pushed as an index (several platforms, or with build attestations, as Docker builds by default) is one image: its parts are no longer listed and scanned as images of their own, and attestations aren't reported as failures. Images built only for arm64 are scanned as arm64. When nothing else says which repository builds an image, the one repository of the entity with the image repository's name is shown as its builder. GitHub refusing to list an organization's container packages to a GitHub App is no longer reported as a gap you could close.
- **Container images, from the repository that builds them to where they run.** Keelson lists the images in Amazon ECR, Alibaba Cloud Container Registry (Enterprise Edition) and GitHub Container Registry, and scans the ones that matter with Aqua's [Trivy](https://github.com/aquasecurity/trivy) when it is installed where Keelson runs (`KEELSON_TRIVY`, or `trivy` on the PATH; not in the Docker image yet): every image a workload runs, images pulled in the last 30 days, the newest of each repository, and the images your workloads run from public registries such as Docker Hub. A new **Images** page shows each image with its vulnerabilities, operating system and stored credentials, the workloads that run it (ECS services, Elastic Container Instance groups, Function Compute functions built from an image), whether the internet reaches them and through which load balancer and hostnames, and the repository that builds it (from the image's source label, the GitHub package's repository, or a workflow that pushes an image of its name). Tabs list running workloads, vulnerabilities and components across every image, with filters for in use, internet-facing, known exploited, has a fix, operating system or application packages; rows can be picked to copy or download. An image's own page says where each vulnerability is fixed: the base image, the repository's code, a rebuild of an image that is behind its code, or the image's build. A repository's page lists the images it builds.
- **Image findings, rated by exposure.** Four checks per platform (`AIM-` on AWS, `LIM-` on Alibaba Cloud, `GIM-` on GitHub): an image in use with a vulnerability attackers are exploiting (CISA's catalog), with critical or high vulnerabilities that have a fix, or on an operating system or runtime past its end of life, and a credential stored in an image (in a file, an environment variable or the build history; only its kind and place are kept). A finding is one per image repository, whatever the tag, rated higher when the internet reaches the workload that runs it than when it runs inside the network; images nothing runs or pulls are listed without findings.
- **To scan images, give Keelson permission to pull them.** On AWS, add an inline policy to the access key's user that allows `ecr:GetAuthorizationToken`, `ecr:BatchGetImage` and `ecr:GetDownloadUrlForLayer` (SecurityAudit doesn't; all three only read). On Alibaba Cloud, replace the RAM policy with the one Add accounts shows: it gains the Container Registry and Elastic Container Instance reads, and `cr:PullRepository`, the one action in it that reads data, which you can leave out. Until then images are listed and the pull is a coverage gap. GitHub needs nothing new: public packages are scanned, and private ones are listed only, because GitHub's registry refuses a GitHub App. Trivy gets a registry login that expires within hours, for that registry only, and never an account's own credential.

- **Pick rows and copy what you need.** On Dependencies, tick packages, vulnerabilities or licenses (or tick the page, then **Select all N that match** to take every row the filters match, across pages), then **Copy** the repositories they affect as `owner/repo` or as links, the packages, advisory or CVE IDs, or the upgrades to make, or **Download affected repositories** as CSV with each repository's packages and the version that fixes them. A package's own window has **Copy repositories** too. Repositories and Attack surface get the same checkboxes, with copying names, links, addresses, open ports (`address:port`) and hostnames, and a CSV of the picked rows. Selected findings can be copied as resources, locations, links, or one line each for a ticket. Zones, Projects and Resources copy what's shown, and Resources downloads it as CSV. Copying works on a team server over plain HTTP too.
- **Find packages and repositories by language.** Dependencies has a **language** filter on every tab (each package manager under the language it's for: npm under JavaScript and TypeScript, PyPI under Python, Maven under Java and Kotlin…), and the search finds packages by language or package manager ("python", "maven"). Repositories has language and visibility filters, and its search matches languages. The packages CSV gains a `language` column at the end.
- On Dependencies, the repository filter could credit an organization's repositories to another account when the view held an account without dependencies before it. Each repository now stays with its own account.
- **Compliance checklists for ISO/IEC 27001 and PCI DSS, as an indication.** A new **Compliance** page lists every Annex A control of ISO/IEC 27001:2022 and every section of PCI DSS v4.0.1's twelve requirements, with what Keelson's checks can say about each in the accounts in view: **failing** (a check behind it has an open finding), **passing** (every check behind it ran and nothing is open), **not enough permission** (a check behind it couldn't read what it needs), **undetermined** (none of its checks apply to the accounts in view, or one is turned off), or **out of scope** (policies, people and premises, which no configuration shows). Open a requirement to see the checks behind it on every platform, what each found, and which parts of it they cover. Statuses follow the latest scans and your triage: accepted risks don't fail a requirement. For PCI DSS, pick the accounts in your cardholder data environment with the view picker. The checklist exports as CSV. It's an indication from what Keelson reads, not an assessment or a certificate, and asks you for nothing.

- **Adding accounts has its own pages.** **Accounts → Add accounts** opens a catalog of every platform, grouped by kind (cloud, edge and hosting, code, from the internet) and searchable by name or service, with how many of each platform's accounts are already connected. Keelson signs every request itself and sends only GETs, and refuses any action that isn't a read in that policy. Checks are judged the way Alibaba Cloud works. They cover RAM (the main account's AccessKeys and MFA; console users without MFA, rated with whether the account requires MFA at sign-in and critical for administrators; users allowed to create their own AccessKeys; one user used by a person and by programs; old and unused AccessKeys; the password policy; administrators with AccessKeys; policies that allow everything or let an identity give itself more access; roles any account or any GitHub repository can assume, or that accounts outside the entity are trusted on). OSS: public buckets after Block Public Access, critical when anyone can write or ActionTrail delivers there, with the CDN fix when Alibaba Cloud CDN serves one; bucket policies that let other accounts in. Network: security groups open to the internet rated by what they're attached to, and CLBs or NLBs that pass SSH, RDP or a database port from anyone, which the security groups don't show. ECS: metadata without a token, credentials in start-up scripts and launch templates, internet-facing Linux instances that take SSH passwords, disk encryption by default per region, images shared outside the entity. Databases: RDS, Tair (Redis) and MongoDB whitelists that admit every address (critical with a public endpoint), Tair and MongoDB that let the VPC in without a password, TLS and TDE. Also ALBs and CLBs that serve plain HTTP or old TLS, CDN domains without HTTPS, ACK clusters with a public API server, anonymous Function Compute triggers and credentials in their variables, KMS rotation and keys pending deletion, ActionTrail, flow logs and Security Center's agent, and Alibaba Cloud DNS records that dangle. Prowler's Alibaba Cloud checks that test compliance wording or a purchase rather than exposure are left out. Its resources have their own page, **Resources**: every instance, load balancer, bucket, database, function, cluster, security group, RAM user and role, in Alibaba Cloud's words, with how the internet reaches it and its open findings, filtered by kind, region (named, and only those in use), exposure and findings.
- **Checks that span platforms include Alibaba Cloud.** Cloudflare records that point at an OSS bucket, load balancer or CDN domain the entity's Alibaba Cloud accounts don't have, or at an EIP they released; an Alibaba Cloud origin behind Cloudflare that accepts anyone (and Cloudflare's exposed-origin check now reads Alibaba Cloud's security groups too); Alibaba Cloud DNS records that point at a Vercel hostname no project serves, an AWS resource or address the entity doesn't have, or a GitHub Pages site no organization publishes; Route 53 records that point at an Alibaba Cloud resource or address the entity doesn't have; and RAM roles GitHub Actions can assume from outside the entity's organizations or from any branch.
- **Sonar watches Alibaba Cloud too.** It starts from Alibaba Cloud DNS's records and the addresses Alibaba Cloud accounts hold, follows hostnames into ALBs and CLBs down to their backend servers, and reports a backend anyone can reach without the load balancer, a public hostname on an internal load balancer, and a rule DNS no longer uses.
- Credentials found in configuration now include Alibaba Cloud AccessKeys, on every platform that scans for them.
- **Findings say where they are in your infrastructure.** A finding that names an address or a hostname, from any platform (Cloudflare Security Center's reports included), shows the DNS records, CNAMEs and load balancers it goes through and the AWS or Alibaba Cloud instance or load balancer, Vercel project or GitHub Pages site that holds it, with a link to it. Otherwise it says that none of the entity's connected accounts holds it, or that one released it. A finding about RDP, SSH or a database port also says whether the holder's security groups or listeners really let anyone reach the port.
- AWS roles that GitHub Actions can assume are judged correctly when their trust policy uses GitHub's immutable subjects (`repo:owner@ID/repo@ID:…`, the default for repositories created since July 2026). They were read as an organization outside the entity.

## 0.15.0

- **A software bill of materials for every GitHub repository.** When Anchore's Syft, Grype and Grant are installed where Keelson runs (on the `PATH`, or their paths in `KEELSON_SYFT`, `KEELSON_GRYPE` and `KEELSON_GRANT`), each GitHub scan keeps an SBOM of every repository from its manifest and lock files, matches its packages with known vulnerabilities, and sorts their licenses. Keelson fetches only manifest and lock files, workflows and Dockerfiles, never the code, and makes a repository's SBOM again only when one of them changes; Grype runs on every scan, so a vulnerability published today is found in code that didn't change. New findings, in a new **Supply chain** category: a dependency with a vulnerability attackers are exploiting (CISA's catalog), one with a critical or high vulnerability or one likely to be exploited soon (FIRST's EPSS), a known malicious package, third-party actions used by a tag that can be moved, projects that install dependencies without a lock file, and dependencies under a strong copyleft license. A package used only for development, or only through other packages with no vulnerability FIRST's EPSS rates 1% or more likely to be exploited within 30 days, is rated one step lower; one attackers are exploiting never is. One finding per package and repository: its evidence gives the smallest upgrade that fixes it, which project of a monorepo uses it (directly or through another package, and whether only for development), each vulnerability with its chance of exploitation, and whether Dependabot reports it. The **Repositories** page shows each repository's packages and worst vulnerabilities, and a new page per repository lists its projects, every package and its license, and downloads the SBOM as CycloneDX, SPDX or Syft JSON. The GitHub App needs one more permission: under Permissions & events → Repository permissions, set **Contents** to **Read-only**, then accept the change on each organization. Grype keeps its vulnerability database (about 3 GB) in the data folder and downloads it from Anchore on the first scan. The tools aren't in the Docker image yet; without them, or without the permission, the Accounts page lists what's missing and the other GitHub checks run as before. "Dependency with a critical or high vulnerability" from Dependabot now counts in Supply chain too.
- A permission the organization grants the GitHub App later is used on the next scan, instead of up to 50 minutes later.
- **A Dependencies page** lists every package across the repositories in view, one row per package and version, most urgent first. Filter by status (vulnerable, exploited, has a fix, no fix yet, malicious, no known vulnerability), severity, package manager, repository, license risk, direct or through other packages, runtime or development only, and the triage of its findings; open a package to see its vulnerabilities and every repository that uses it, with where and its finding. The **Vulnerabilities** tab lists each vulnerability with the packages and versions it affects, and the **Licenses (Grant)** tab is Grant's report: each license with its risk class and how many packages and repositories have it. The filtered packages export as CSV. Each repository's page now has its own license summary.
- Licenses are classified per package from its own license expression, so a package version that states its license in one repository's lock file is no longer left unclassified because another repository's lock file doesn't state it.

## 0.14.0

- When the browser can't reach the Keelson server, the page now says so in a card like the sign-in page's, explains what to do, and tries again every 5 seconds, so a restarted server brings it back without a reload. Links across the app now use the design system's own link, the one-time password for a new user has its own copy control, and the expand buttons on Findings and Triaged match the rest.
- **Sonar follows each hostname into AWS.** The Attack surface page shows, for every hostname, the load balancer its DNS names (internal or internet-facing, with what its security groups admit and whether a WAF web ACL filters it), the listener rules a request for it can take, in the order the load balancer tries them, and the targets behind each rule, down to whether a target has its own public address and security groups that let anyone reach it. Hostnames are followed through CNAMEs to the entity's own names, so a proxied hostname whose origin name points at a load balancer shows it, and through a network load balancer to the application load balancer behind it, and validation and DKIM records are no longer listed as hostnames. A new **Load balancers** tab lists each one with the hostnames that reach it, its rules and its targets, and addresses show what their security groups let anyone reach next to what Shodan has seen. New findings: a load balancer's target that anyone can reach without the load balancer, skipping its WAF and TLS (critical when the rule signs visitors in first); a public hostname that points at an internal load balancer; and a load balancer that still routes a hostname no DNS record points at it. A database or remote-administration port Shodan saw is rated one step lower when the AWS account that holds the address no longer lets anyone reach it. AWS scans now read listener rules, target groups and their targets (`elasticloadbalancing:DescribeRules`, `DescribeTargetGroups` and `DescribeTargetHealth`, part of the SecurityAudit policy); a header condition's value is never kept. Scan the entity's AWS accounts, then Sonar, to see it.
- DNS records that point at a network load balancer (`<name>.elb.<region>.amazonaws.com`) are now recognised as AWS, like application and classic load balancers' names were, so checks for records that point at a deleted load balancer cover them too.
- **Sonar runs OWASP Amass** when it is installed where Keelson runs (on the `PATH`, or its path in `KEELSON_AMASS`), on the domains of every connected account in the entity. Amass runs passive and limited to those domains, for up to 10 minutes, and its engine listens on port 4000 while it runs; if the engine stops, the Accounts page says why. Hostnames it adds are marked "Amass". The Docker image doesn't include Amass yet; without it, the Accounts page lists it as a source that couldn't be read, and everything else works as before.
- **Sonar: external attack surface.** Keelson can now look at an entity from the internet. Turn it on with **Watch from the internet** on the new **Attack surface** page or on an entity's card under Accounts. A Shodan API key is optional; add it then, or later from the Internet account's menu (**Add a Shodan API key**). Starting from the domains, DNS records and addresses of the entity's other accounts, Sonar finds more hostnames in certificate transparency logs (crt.sh) and Shodan, looks them up in public DNS, and asks Shodan what it has seen open on the entity's addresses. It is passive: nothing is sent to your hosts. New findings: databases and caches open to the internet, remote administration open to the internet, software with known vulnerabilities, the origin of a Cloudflare-proxied hostname that anyone can find on Shodan (high when the entity's AWS account says its security groups let anyone in), a recent certificate from an authority the domain's CAA records don't allow, and domains whose DNS no connected account serves.
